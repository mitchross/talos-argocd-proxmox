01Verified configuration faultOffsite validation pending

Fix the DNS destination, then test remotely.

Tailscale distributes 192.168.1.1 as global DNS. The only approved router for that subnet, tailscale-firewalla, was offline. Technitium at 192.168.10.15 correctly answers your domain.

The online TrueNAS Tailscale app advertises an approved route for 192.168.10.0/24. That route reaches your actual LAN, but does not cover 192.168.1.1.

Recommended change: use 192.168.10.15 only for vanillax.me. Use reachable public resolvers, or the client's local DNS, for other domains. This is called split DNS: the hostname's suffix selects its resolver.

Proposed procedure

Prerequisites: access to Tailscale DNS/network administration; a saved copy of existing DNS settings; a phone on cellular or another genuinely offsite client. Recheck the TrueNAS subnet route and intended client permissions first.

  1. Remove the stale global 192.168.1.1 nameserver. Choose either reachable public global resolvers or clients' local DNS; review the global override accordingly.
  2. Add 192.168.10.15 as a restricted nameserver for vanillax.me.
  3. Keep the NAS's approved 192.168.10.0/24 route. Ensure intended clients can reach the DNS server on TCP/UDP 53 and the app gateway on HTTPS.
  4. Enable “Use Tailscale DNS” on the test client. Linux clients also need accepted subnet routes. Review “Use with exit node” if the client uses one.
  5. On cellular, check private resolution, unrelated public DNS, and an actual HTTPS app.

Success looks like this

  • argocd.vanillax.me resolves to 192.168.10.52.
  • news.vanillax.me resolves publicly, and google.com also resolves.
  • The private app opens over HTTPS. Correct DNS alone does not prove application routing works.

On a connected Mac, check the system resolver with this read-only command:

dscacheutil -q host -a name argocd.vanillax.me

Avoid a misleading local test. This Mac received DNS answers even when querying TEST-NET address 192.0.2.123, consistent with LAN DNS interception. Therefore, successful LAN queries to an arbitrary address do not prove that address is reachable through Tailscale. Technitium container-loopback tests bypassed that interception.

If validation fails: separate DNS resolution from subnet reachability. If names resolve but HTTPS fails, inspect client route acceptance and access policy. Restore the saved DNS settings to undo the change, understanding that the old global resolver still depends on the offline router.

Do not blindly toggle NAS settings: its accept-dns=false and accept-routes=false govern the NAS itself. They do not disable its advertised subnet routing for other clients.

Confidence boundary: the configuration fault is verified. All other tailnet peers were offline during inspection, so the user's offsite symptom and proposed remediation were not tested end to end. Tailscale DNS reference · Subnet-router documentation.

Two observation windows

72-hour history: 432 ten-minute averages from existing Netdata metrics. CPU mean 1.51%, p95 2.43%, maximum ten-minute average 11.88%. These averages can hide brief spikes. Demand-data hit rate was calculated from access/hit rates because the supplied percentage chart returned invalid zeros.

Five-minute live sample: 20 September, 17:16:08–17:21:08 UTC. Demand-data reads: 405,024 hits and 15 misses, or 99.9963%. CPU averaged 3.68%; the highest 15-second sample was 10.98%. Traffic averaged 8.51 MiB/s inbound and 6.56 MiB/s outbound. The highest observed HDD utilization over a 15-second sample was 27.5%.

There was no observed CPU, disk, or memory saturation during that workload. That does not test the NAS at maximum load.

Why the smaller-cache history is only a clue

About 11 hours of historical buckets had ARC below 128 GiB and roughly 99.999967% demand-data hits. That suggests some workloads fit comfortably in less cache. Those periods had different activity and cache warm-up conditions, however, and do not simulate a machine with only 128 GB total RAM.

Read-test controls and limitations

Tests used existing allocated files, one job, queue depth 1, 1 MiB blocks, fixed byte limits, and 15-second caps. The total was 3.25 GiB. Disk counters confirmed approximately 1,024 MiB of physical reads for the direct test and 1,082 MiB for the buffered first read. The immediate repeat was primarily cached.

An old seq_write.test file was excluded: it appeared to be 4 GiB but had only 512 bytes allocated. Reading its holes would produce a misleading “disk” benchmark. No raw-disk tests, writes, installs, cache drops, or ARC-limit changes were used.

The earlier NAS performance reference reports 408 MB/s local disk reads, 1,119 MB/s raw TCP, and 141–243 MB/s writes across tested paths. Those results were not reproduced in this investigation. Different files, cache state, and test conditions prevent a regression claim. Its NFS/SMB write comparison also mixes sync=disabled and sync=standard; it does not isolate protocol overhead.

The next experiment that would answer the RAM question

  1. Choose an acceptable workload target: backup completion window, restore duration, Steam behavior, and file-open latency.
  2. Record a full representative workload cycle with current RAM: app memory peaks, demand-data hit/miss rates, disk latency/queues, and task duration.
  3. In a planned experiment, compare smaller ARC budgets while reserving enough memory for the OS and application peaks. Changing ARC size alone is not a perfect simulation of smaller physical RAM.
  4. Repeat comparable workloads after a defined warm-up period. Keep a configuration record and restore the original ARC settings if latency, memory pressure, or task duration worsens beyond the chosen target.
  5. Use the observed difference and hardware price to choose between 128, 256, and the current capacity.

This is a proposed experiment, not a change performed during the audit. ARC interpretation: OpenZFS caching and ARC statistics.

What the Pi is doing

The Pi runs Ubuntu on ARM64 with about 7.7 GiB RAM. ProxCenter's frontend and PostgreSQL used approximately 140 MiB and 27 MiB respectively in one snapshot. Around 6.1 GiB was available overall. Omni, its five providers, and Technitium also run there. There is no measured resource reason to move the dashboard.

If you want to try PDM

Use an x86-64 Debian VM, outside the Kubernetes application stack if it will be a recovery tool. An evaluation based on upstream recommended resources would start with two vCPUs, 4 GiB RAM, and at least 40 GB disk. Add standalone hosts as remotes with the permissions needed for the trial. Verify inventory and a harmless operation on a disposable guest. PDM downtime does not itself stop the managed guests. Official installation requirements.

Rollback: remove the trial remote connections and evaluation VM when no longer needed, after revoking its credentials. This does not require changing the PVE topology.

When a real cluster becomes worth it

Revisit a three-node, reliably wired design when you have a specific guest-failover requirement, a compatible storage plan, and enough spare capacity for failures. Keep the shed out of that quorum proposal. Proxmox calls for stable sub-5 ms networking and recommends separating Corosync from heavy storage traffic. HA also requires addressing passthrough, CPU compatibility, and guest storage; joining hosts alone does not solve them.

In-cluster feasibility, public ingress architecture, and pilot checks

Can the control plane run in Kubernetes?

Yes, technically. Modern self-hosted deployments combine management, signal, relay, and STUN in netbird-server, with a dashboard and embedded identity support. The upstream quickstart starts at one CPU and 2 GB RAM; that is a provisioning baseline, not a measurement of this lab.

HTTP, WebSockets, OAuth, and gRPC/h2c must route correctly. Public UDP 3478 for STUN needs direct reachability; a Cloudflare HTTP Tunnel cannot supply it. Home hosting therefore needs appropriate inbound reachability, or an external endpoint such as a VPS. Quickstart · Proxy and transport requirements.

Inside this repository, an implementation would need pinned manifests, named Services, explicit network permissions, 1Password-managed secrets, backed-up state, and an update strategy appropriate for a single-writer database/PVC. Kubernetes, Cilium, secrets, and storage then become dependencies of remote access.

Two integration details to verify

  • The official server Helm chart source inspected in the investigation still described the older split-service architecture (chart 1.9.0 / app 0.46.0). Verify it against the intended current release before using it. The Kubernetes operator attaches services to an existing management account; it is not the control-plane server.
  • NetBird Gateway API integration exists, but upstream labels it beta. Its self-hosted public-proxy documentation identifies Traefik as the supported external TLS-passthrough edge. This is not a verified drop-in substitution for this lab's Cilium gateway.

Acceptance and rollback

  1. Pick private VPN access or public ingress as the first goal.
  2. Test one client and one noncritical resource while the existing path remains available.
  3. Verify DNS, intended access policy, reconnect behavior, direct versus relayed paths, and usable throughput.
  4. Test recovery access during an isolated pilot-component outage; do not take down the production cluster to prove it.
  5. Only replace an existing endpoint after behavior meets your needs. Roll back by returning clients/DNS to the original path and removing pilot routes and credentials.

Switching VPN products would not automatically repair Technitium routing or the current DNS policy. Those dependencies must be configured in either product. This investigation did not verify that Cloudflare Access authentication is active; do not assume a tunnel alone supplies it.

05Small isolated pilotExact version combination untested

The TrueNAS plugin fits. Start with one test VM.

Install it on a Proxmox host to let Proxmox request TrueNAS-backed VM disks and ZFS snapshots. It automates block storage; it is not a ProxCenter replacement, a TrueNAS App, or a requirement to form a Proxmox cluster.

Its immediate value is automatic zvol provisioning and snapshots over iSCSI or NVMe/TCP. It does not establish that HDD-backed NAS disks outperform your local storage. NFS/SMB still serve file content such as ISOs and backups. TrueNAS's September announcement calls for early-adopter testing on non-production workloads.

Your specific collision risk: all five independent hosts have VM 100. Each standalone host needs its own parent dataset and its own iSCSI target or NVMe subsystem. A common dataset can collide at the zvol level. Distinct datasets with one shared target still expose unrelated block devices. Upstream isolation guide.

The smallest useful pilot

  1. Choose one wired host, such as 192.168.10.14, and a disposable VM.
  2. Use a dedicated dataset such as BigTank/proxmox-pilot-pve14 with its own target, separate from Steam iSCSI and Kubernetes storage.
  3. Use an inspected, pinned package and start with iSCSI. Keep the source VM disks/local recovery path until the trial passes.
  4. Verify creation, guest I/O, resize, snapshots/rollback, clone, backup/restore, deletion cleanup, and movement back to local storage.

Compatibility, release gotchas, permissions, and storage failure domains

Broad prerequisites match; exact compatibility remains untested

All hosts run PVE 9.2.18. The NAS runs TrueNAS-26.0.0-MASTER+20260914-020141. Upstream's minimum is TrueNAS 25.10+ and PVE 8+ for iSCSI, or PVE 9+ for NVMe/TCP. The development NAS version meets that broad floor but requires testing against the chosen plugin release.

On .14, open-iscsi and nvme-cli were present and the plugin was absent. NAS iSCSI and NVMe-oF services were running. PVE's live storage API version was 15 with compatibility age 6; an older plugin API declaration alone is not proof of incompatibility.

Choose matching release artifacts

On 20 September, v2.1.23-beta4 was the newest published release (19 September; marked prerelease). GitHub's “latest” endpoint selected beta3, whose prerelease flag was false despite its beta name. The main-branch version banner was older still. Pin a coherent package/tag and its matching configuration documentation; do not combine moving-branch installer files and unrelated release instructions.

The Reddit discussion mentions a dataset-creation bug and a beta-tag installer error. Tagged source shows several historical defects already fixed, including the PR82 dataset issue, later cloud-init changes, and beta4 capacity-cache/FQDN fixes. Open issue titles alone do not establish that the chosen release still fails. No plugin runtime defects were reproduced here.

Beta4 release · Tagged changelog · Cleanup/VMID-reuse report to validate.

Credentials and isolation

Use a dedicated API identity, verify the documented roles against the installed TrueNAS version, and keep credentials in 1Password and private host storage. Keep TLS verification enabled with a trusted matching certificate. Dataset write/delete roles may grant appliance-wide capabilities: selecting a pilot dataset prevents naming collisions but does not necessarily restrict the API key to that dataset. Restrict storage initiators as appropriate. API permissions guide.

Keep the current Talos storage design during the trial

Most active Talos disks are on per-host local LVM-backed storage. Moving their Longhorn storage disks onto this one NAS would place those volumes—and any replicas hosted there—behind the same physical NAS dependency. The plugin does not remove GPU/USB passthrough or mixed-CPU migration constraints.

For important future VM data, use a redundant pool. The current ai-pool is intentionally striped without redundancy. Snapshot support does not replace independent backups. Adding VM workloads would also change the NAS working set, so revisit RAM sizing after that change rather than applying today's measurements unchanged.

Stop conditions and rollback

Stop the pilot on unexplained data-integrity errors, failed cleanup, or a failed move back to local storage. Preserve logs and the exact version; do not test deletion on production volumes. Restore the disposable guest from its known-good backup or local copy. After ensuring no guest uses the pilot backend, remove only the pilot storage configuration, targets, data, and credentials. Do not stop shared NAS services to remove the trial.

Any future repository-owned implementation follows the branch/PR workflow. Host installation and storage changes need a concrete deployment plan; this report is the assessment, not that deployment.
