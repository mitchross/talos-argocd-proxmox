Fix the DNS destination, then test remotely.

Tailscale distributes 192.168.1.1 as global DNS. The only approved router for that subnet, tailscale-firewalla, was offline. Technitium at 192.168.10.15 correctly answers your domain.

The online TrueNAS Tailscale app advertises an approved route for 192.168.10.0/24. That route reaches your actual LAN, but does not cover 192.168.1.1.

Recommended change: use 192.168.10.15 only for vanillax.me. Use reachable public resolvers, or the client's local DNS, for other domains. This is called split DNS: the hostname's suffix selects its resolver.

Proposed procedure

Prerequisites: access to Tailscale DNS/network administration; a saved copy of existing DNS settings; a phone on cellular or another genuinely offsite client. Recheck the TrueNAS subnet route and intended client permissions first.

  1. Remove the stale global 192.168.1.1 nameserver. Choose either reachable public global resolvers or clients' local DNS; review the global override accordingly.
  2. Add 192.168.10.15 as a restricted nameserver for vanillax.me.
  3. Keep the NAS's approved 192.168.10.0/24 route. Ensure intended clients can reach the DNS server on TCP/UDP 53 and the app gateway on HTTPS.
  4. Enable “Use Tailscale DNS” on the test client. Linux clients also need accepted subnet routes. Review “Use with exit node” if the client uses one.
  5. On cellular, check private resolution, unrelated public DNS, and an actual HTTPS app.

Success looks like this

  • argocd.vanillax.me resolves to 192.168.10.52.
  • news.vanillax.me resolves publicly, and google.com also resolves.
  • The private app opens over HTTPS. Correct DNS alone does not prove application routing works.

On a connected Mac, check the system resolver with this read-only command:

dscacheutil -q host -a name argocd.vanillax.me

Avoid a misleading local test. This Mac received DNS answers even when querying TEST-NET address 192.0.2.123, consistent with LAN DNS interception. Therefore, successful LAN queries to an arbitrary address do not prove that address is reachable through Tailscale. Technitium container-loopback tests bypassed that interception.

If validation fails: separate DNS resolution from subnet reachability. If names resolve but HTTPS fails, inspect client route acceptance and access policy. Restore the saved DNS settings to undo the change, understanding that the old global resolver still depends on the offline router.

Do not blindly toggle NAS settings: its accept-dns=false and accept-routes=false govern the NAS itself. They do not disable its advertised subnet routing for other clients.

Confidence boundary: the configuration fault is verified. All other tailnet peers were offline during inspection, so the user's offsite symptom and proposed remediation were not tested end to end. Tailscale DNS reference · Subnet-router documentation.

What happens with four simultaneous file transfers?

A follow-up used four distinct 1 GiB files. Four disk readers achieved 522 MB/s total, about 131–135 MB/s each. Four writers achieved 202 MB/s total, about 51 MB/s each, including each job’s final flush. One reader over the same four files reached 434 MB/s. All disk reads were verified with physical counters.

That is an actual four-stream NAS-local test. It is not a four-user SMB test, a mixed read/write test, or a claim that throughput scales linearly as users are added. Four-stream measurement evidence.

Why the smaller-cache history is only a clue

About 11 hours of historical buckets had ARC below 128 GiB and roughly 99.999967% demand-data hits. That suggests some workloads fit comfortably in less cache. Those periods had different activity and cache warm-up conditions, however, and do not simulate a machine with only 128 GB total RAM.

Benchmark controls and limitations

The complete NAS suite ran 17:45:56–17:54:58 UTC: 24 tests on three new 8 GiB-quota scratch datasets. Disk phases used primarycache=metadata, secondarycache=none; warm phases used primarycache=all after a warmup read. Metadata caching remained enabled. Prefetch can generate ARC demand hits while reading from disk, so physical disk-byte deltas establish the data path.

Sequential writes used buffered I/O plus end_fsync=1; random writes used fsync=1. The latter’s full write cycle includes both the write and separate fsync. All temporary datasets were removed, production properties were unchanged, and the pools stayed healthy. No global cache drops or ARC-limit changes were performed.

The first small read-only pass is preserved as historical evidence in the NAS reference. Its 96.7 MB/s old-file direct read is not the pool maximum. An old 4 GiB sparse file with only 512 bytes allocated was excluded. Historical NFS/SMB tests used different sync settings and do not establish protocol overhead.

The next experiment that would answer the RAM question

  1. Choose an acceptable workload target: backup completion window, restore duration, Steam behavior, and file-open latency.
  2. Record a full representative workload cycle with current RAM: app memory peaks, demand-data hit/miss rates, disk latency/queues, and task duration.
  3. In a planned experiment, compare smaller ARC budgets while reserving enough memory for the OS and application peaks. Changing ARC size alone is not a perfect simulation of smaller physical RAM.
  4. Repeat comparable workloads after a defined warm-up period. Keep a configuration record and restore the original ARC settings if latency, memory pressure, or task duration worsens beyond the chosen target.
  5. Use the observed difference and hardware price to choose between 128, 256, and the current capacity.

Consolidation and buying priorities

  1. Protect the data before removing a host. Identify every sole volume copy, retain independent replicas or proven recovery, and account for the single control plane on SFF. Losing that host stops scheduling even when workers have spare capacity.
  2. Investigate SFF contention and storage latency. Its six host threads serve ten assigned vCPUs. Pretest CPU steal affected both worker and control plane; etcd WAL p99 exceeded 10 ms in about 9% of sampled windows. Buying more fleet-wide CPU does not isolate this problem.
  3. Prioritize expandable RAM on a future wired consolidation host. Elite has about 4 GiB host-available memory and 18.26 of 22.98 GiB Kubernetes allocatable memory reserved by requests. Rebalance eligible apps before assuming an immediate purchase is necessary.
  4. Choose dependable SSD storage for durable state. Investigate the slow measured paths and monitor Elite’s VM SSD at 75% endurance used. This is wear tracking, not a prediction of imminent failure. Preserve the NAS’s useful RAM.
  5. Evaluate Dell retirement first, only after migration checks. An optimistic request/placement model fits its 32 displaced application pods elsewhere. Dell still carries two sole data copies and one copy of each of five protected volumes. The model is not proof that draining it will succeed.

Planning assumption: preserve today’s applications with room to grow. A future host should be sized for eligible workloads’ requests and observed peaks, plus OS/storage overhead and the spare capacity needed during a failure. No single new-machine RAM number is justified until the destination roles and failure target are chosen.

Seven real Kubernetes volume paths, limitations, and the benchmark restart

Revised guest tests used one Python process, a new 512 MiB file, 1 MiB direct-I/O sequential writes/reads, and 128 separate 8 KiB writes with fsync. Every direct-write phase included a final fsync. Guest/client page cache was bypassed for sequential I/O; upstream caches and production traffic remained.

The NAS SMB dataset has sync=disabled, verified live. Its fast fsync replies do not establish durable storage and should not be compared as equal guarantees with the Longhorn paths. The read can come from NAS ARC.

The GPU enterprise path saw about 8.1 GB of guest-device reads while the benchmark itself read about 0.54 GB. Its 46.8 ms write-cycle p99 reflects a busy application path; it does not establish that enterprise drives are intrinsically slower. These tests cross different layers, so subtracting a host result from a guest result would not measure “Longhorn overhead.”

Subsequent tests used 512 MiB direct I/O, checked available cgroup headroom where exposed, and completed cleanup.

The seven revised tests completed without reported benchmark errors. No raw VM disk, production file, resource limit, or scheduling configuration was changed. Hot, slow, or underused: how to interpret the warning signs

Hot: NAS HDDs at 54–58°C justify checking cooling. Threadripper’s 103.6°C sensor was Tctl, not the die temperature; Tdie peaked at 76.6°C in the historical query. Interpret sensor labels before diagnosing overheating. Linux AMD temperature-sensor definitions.

Slow: the shed’s remote path, SFF contention, and some storage tail latency deserve attention. Etcd’s WAL p99 exceeded the upstream 10 ms guideline in about 9.14% of sampled windows; backend commit p99 exceeded 25 ms in about 0.99%. Etcd performance guidance.

Underused: NAS CPU and some guest memory have headroom in observed activity. That does not mean unused hosts can be switched off: 44 volumes have their only copy on GPU, the shed is tainted against ordinary scheduling, Elite has attached devices, and SFF owns the sole control plane. Four pretest OOM counter events on each of GPU and Elite remain unattributed; do not equate them automatically with host RAM exhaustion.

In-cluster feasibility, public ingress architecture, and pilot checks

Can the control plane run in Kubernetes?

Yes, technically. Modern self-hosted deployments combine management, signal, relay, and STUN in netbird-server, with a dashboard and embedded identity support. The upstream quickstart starts at one CPU and 2 GB RAM; that is a provisioning baseline, not a measurement of this lab.

HTTP, WebSockets, OAuth, and gRPC/h2c must route correctly. Public UDP 3478 for STUN needs direct reachability; a Cloudflare HTTP Tunnel cannot supply it. Home hosting therefore needs appropriate inbound reachability, or an external endpoint such as a VPS. Quickstart · Proxy and transport requirements.

Inside this repository, an implementation would need pinned manifests, named Services, explicit network permissions, 1Password-managed secrets, backed-up state, and an update strategy appropriate for a single-writer database/PVC. Kubernetes, Cilium, secrets, and storage then become dependencies of remote access.

Two integration details to verify

  • The official server Helm chart source inspected in the investigation still described the older split-service architecture (chart 1.9.0 / app 0.46.0). Verify it against the intended current release before using it. The Kubernetes operator attaches services to an existing management account; it is not the control-plane server.
  • NetBird Gateway API integration exists, but upstream labels it beta. Its self-hosted public-proxy documentation identifies Traefik as the supported external TLS-passthrough edge. This is not a verified drop-in substitution for this lab's Cilium gateway.

Acceptance and rollback

  1. Pick private VPN access or public ingress as the first goal.
  2. Test one client and one noncritical resource while the existing path remains available.
  3. Verify DNS, intended access policy, reconnect behavior, direct versus relayed paths, and usable throughput.

The TrueNAS plugin fits. Start with one test VM.

Install it on a Proxmox host to let Proxmox request TrueNAS-backed VM disks and ZFS snapshots. It automates block storage; it is not a ProxCenter replacement, a TrueNAS App, or a requirement to form a Proxmox cluster.

Its immediate value is automatic zvol provisioning and snapshots over iSCSI or NVMe/TCP. It does not establish that HDD-backed NAS disks outperform your local storage. NFS/SMB still serve file content such as ISOs and backups. TrueNAS's September announcement calls for early-adopter testing on non-production workloads.

Your specific collision risk: all five independent hosts have VM 100. Each standalone host needs its own parent dataset and its own iSCSI target or NVMe subsystem. A common dataset can collide at the zvol level. Distinct datasets with one shared target still expose unrelated block devices. Upstream isolation guide.
