Before hard isolation

Capacity + dependencies

Argo currently occupies GPU, Elite and SFF workers. OTel and other core services lack pool-specific rules. A migration needs room on the remaining hosts.

Pod movement does not relocate Longhorn replicas. GPU/Dell taints should follow a workload and storage inventory.

Four rules that make this realistic
  1. A label is a name, not a reservation. A preferred affinity steers placement; it cannot protect core capacity from experiments.
  2. A toleration grants permission. Pair it with a selector or affinity when a workload must use a specific group. NoSchedule does not evict existing Pods.
  3. A PDB handles voluntary disruption. It does not stop a power failure. A single-replica controller with minAvailable: 1 can block a drain.
  4. Keep real failure domains. General workers share home dependencies; they are not independent cloud availability zones. Spreading applications also does not make a single control plane highly available.

Practice the release decision

Test → promote → verify

Deploy an image digest to the lab target. Check a real service response. Promote the same digest by PR. Revert the target change to practice rollback.

Manual sync is not a pinned release. Shared base changes at main/HEAD can affect both targets. Gate a manifest revision too if the exercise needs to freeze all configuration.

A PostSync smoke test can detect a bad deployment. It does not automatically undo it, and selective sync skips hooks.

Five Argo details worth retaining
  1. Waves have a scope. Root health checks can gate direct children. Applications generated by an ApplicationSet reconcile independently; matching wave numbers do not create a global dependency graph.
  2. Deletion deserves a preview. Moving a directory can change the generated owner. allowEmpty: false is not a general deletion lock.
  3. Shared configuration needs shared invalidation. When adding bases or Components, review discovery, CI coverage and manifest-generation cache hints for all consumers.
  4. Traffic-weight changes need visible diffs. Home ignores HTTPRoute backend weights globally. Review that rule before a weighted-routing exercise.
  5. Keep existing schema and render checks. Add semantic checks for selectors and PDBs where useful. A YAML file can render successfully and still express the wrong policy.

Secret and bootstrap exercises with low upkeep
  • Trace one demo credential: secret-store access, synchronization, Pod consumption and reload after rotation.
  • Record initial trust: home pre-seeds 1Password access; work needs cloud identity and initial GitHub App secret values before Git access succeeds.

What Terraform and ComputeClasses actually provide

The reviewed Terragrunt entries lead through a versioned organization module to Google’s regional GKE module. The configuration includes private control-plane access, node auto-repair/upgrade, fleet registration, KMS-backed encryption and managed prerequisites.

Three zones is source-derived. The wrapper does not specify zone letters; the upstream module chooses three available zones. The infra pool declares 1–2 nodes per zone, implying 3–6 infra workers under that topology. Separate app capacity can grow through ComputeClass node-pool auto-creation.

The standard class declares machine-family fallbacks and consolidation. Namespace labels choose its default for new Pods in GKE. Copying that namespace label onto Talos does not install the GKE behavior.

Three different loops: HPA changes Pod replicas. Node autoscaling changes worker capacity. A PDB limits voluntary eviction. None substitutes for the others.

The GKE wrapper permits an upstream 44.x version range; public defaults were inspected, but the deployed resolved module was not. Resource caps are not a cloud spending budget.

The important correction: telemetry does not have a third pool in this source

The intended topic was workload isolation as well as zone spread. The initial summary gave isolation too little attention.

Rechecking the source found core infrastructure and OTel gateways/scrapers explicitly selecting the same infra class. PoC/app namespaces select the standard class. Node telemetry agents are DaemonSets intended to observe across nodes; their live coverage was not verified.

This establishes two capacity groups in the reviewed configuration. Separate telemetry nodes may be a future design, but the inspected selectors do not establish that third boundary.

Your home already has four role groups. Adding a new pool system would miss the existing design; the useful work is deciding which services consume those roles.

Rendered findings: enterprise configuration still needs review
  1. The ApplicationSet controller does render. The inspected chart 10.2.2 ignores applicationSet.enabled: false; its Deployment is unconditional. The earlier “missing controller” concern was resolved by rendering.
  2. RollingSync is declared but not enabled by the inspected bootstrap. Its runtime feature setting needs verification. If enabled later, stripping normal auto-sync alone does not create a manual production gate.
  3. HA settings are uneven. Some Argo PDBs allow zero available replicas. Argo generally separates hostnames, without explicit zone spread; repo-server, ApplicationSet and Dex render as single replicas.
  4. A spread selector can be wrong while YAML renders. A sampled workload selected another app’s label. The examined target was scaled to zero, making this a latent configuration issue.
  5. Shared modules need matching CI triggers. A shared cluster wrapper is consumed by both environments, but the inspected production path filter can miss edits confined to that wrapper.

These are source/render observations, not claims of live work outages. Some secret-access bindings were also broader than individual secrets; identity federation alone does not establish least privilege.

Keep availability and recovery findings visible
Dated observations, not current alerts. The latest node check in this conversation found all six nodes Ready. Earlier same-day shed/Intercept findings describe the earlier snapshot; the cause of recovery was not established.
  • Git sync and service health differ. The earlier snapshot had 100 Synced Applications, with 92 Healthy, seven Progressing and one Degraded. Intercept depended on a radio attached to the then-unavailable shed node.
  • Recovery is stronger than continuous availability today. There is one control-plane node. Earlier Longhorn inventory had 84 of 89 volume objects configured for one replica, and five for two. Those are volume objects, not 89 business datasets.
  • Historical backup success is insufficient. The earlier Immich library snapshot failed while Postgres snapshots succeeded. The underlying mover cause was not investigated; this report does not claim it is still failing.
  • A recovery claim needs an actual restore. The sampled restore-canary namespace lacked a current drill marker. This neither proves no drill occurred elsewhere nor proves recovery works now.

Keep data recovery, service continuity and pool isolation as separate objectives. A database filesystem backup also does not automatically provide point-in-time recovery.

Other useful exercises, when you want them
  • A tenant sandbox: narrow one demo AppProject’s source, namespace and kinds; add a quota and realistic network dependencies. Existing broad Cilium allowances must be accounted for—an extra restrictive policy cannot subtract them.
  • CI policy practice: validate topology selectors, replica/PDB compatibility and service readiness with passing and failing examples. Keep the existing home-specific contracts.
  • A small failure exercise: use disposable stateless replicas and an agreed maintenance window. Verify service and telemetry behavior; start with a written plan.
  • GKE-specific learning: a separately chosen cloud lab can teach managed IAM, ComputeClasses and cloud networking. Those features are not reproduced merely by renaming home labels.
