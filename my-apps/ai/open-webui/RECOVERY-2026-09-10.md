# Open WebUI and Intercept volume recovery

This change restores two applications from tested backups into new PVCs. It
preserves their failed original PVCs and changes no database or app architecture.
The failure was unreadable, zero-byte Longhorn V1 replica metadata after the host
reboots; this does not establish physical SSD failure.

## What the manifests do

- Keep `open-webui/storage` and `intercept/intercept-postgres-data`, with
  `Prune=false,Delete=false`; their original PVC specs are unchanged.
- Restore into `storage-recovered` (10 GiB) and
  `intercept-postgres-recovered` (20 GiB) using existing passive Restore objects.
  Both use the existing two-copy `longhorn-wired-ha` class.
- Keep backup usernames/hostnames and `/pvc/storage` /
  `/pvc/intercept-postgres-data` paths unchanged through `sourcePathOverride`.
  Schedules now protect the replacement PVCs, in the same backup lineage.
- Use normal `fromPolicy`, `offset: 0`, with explicit original `sourcePath`.
  `onMissingSnapshot: Fail` overrides the shared component's empty-volume default.
  No dated snapshot ID is permanently embedded in either PVC's restore source.

The deployed [kopiur 0.10.8 source](https://github.com/home-operations/kopiur/blob/49addf88fddd33013383224d050066e99059e01a/crates/controller/src/restore/mod.rs)
resolves and pins independently for each claiming PVC. S3 latest selection runs
in the mover. There is **no atomic check against the IDs above before app startup**:
a newer matching backup created after review could be selected. Check latest
successful IDs immediately before merge; if either differs, verify that recovery
point before proceeding. Check each new claim's resolved ID after binding.
Future newly created claims continue selecting latest, without an unpin PR.
Restore and PVC stay in the same sync wave to avoid a populator dependency deadlock.

## Capacity: measured now versus proposed allocation

At 23:33 UTC all three eligible data disks were Ready and Schedulable, with
`wired-storage` tags and distinct Dell, Elite and SFF failure-domain labels.

| Host | Currently available GiB | Currently scheduled GiB |
| --- | ---: | ---: |
| Dell | 365 | 303 |
| Elite | 421 | 123 |
| SFF | 643 | 336 |

The two new volumes add **60 GiB** of replica reservation in total, not 30 GiB.
Allow another **30 GiB** for simultaneous one-copy backup staging; a conservative
per-host allowance is 60 GiB. These are proposed reservations, not measured writes.
Current available space already accounts for approximately 4.3 GB allocated to
the retained failed chains. Snapshot growth and other workloads still consume
headroom. Confirm two running replicas on different hosts after restoration;
replication does not replace backup or protect against shared corruption.

## Acceptance and retained-volume cleanup

After explicit merge approval, let Argo restore before binding. Confirm both new
claims are Bound, their per-claim Restore records completed with the reviewed
IDs, and Longhorn has two healthy copies on distinct eligible hosts. Confirm
WebUI login, existing chats and document search, and Intercept database readiness
and ADS-B ingestion. Run one native Snapshot for each existing policy and confirm
successful, nonempty backups retain the original source identity. A Ready pod
alone is not proof of recovery.

Keep the old data until the user accepts recovery; switching back to it would
return to the original fault. Preserve any new writes before a rollback. After
`Prune=false,Delete=false` has actually synced, remove **only the two old PVC
manifest documents** in a separate reviewed cleanup PR. Argo will leave their
live PVCs/data retained, while future cluster bootstraps stop creating unused
duplicate claims. Explicit later data-deletion approval is separate. This cleanup
is not an unpin step: the replacement volumes already restore from latest.
