# Porting a whole app to another language (multi-PR hand-off)

Use this when the user asks to "rewrite X in <language>". The job is bigger than one child session, so plan it in phases and hand off one phase at a time.

## 1. Size it before you agree
- Count lines per component (`wc -l` by directory, and tests apart from code). Find the runtime deps that are hard to port: browser automation (Playwright/CDP), workflow SDKs (Temporal), ML libs, and the frontend.
- Check the target language's SDK maturity on the web (for example the Temporal Rust SDK's GA status and version). Don't go from memory.
- State the risks plainly: recently fixed bugs coming back, and weaker libraries on the target side. Recommend the smallest scope.
- Ask one `clarify` with independent questions: **scope** (part by part / backend only / everything / trial piece) and **why** (perf, type safety, one language, learning). The motivation decides what to optimise for. If the answer is "everything" or "one language", ask a separate follow-up about the **browser UI**: keep the static HTML/JS served by the new server, use server templates, or go full WASM. Never assume the UI moves.

## 2. Phase plan (one PR per phase)
1. Pure logic library (classifier, pricing, rules), with tests ported.
2. HTTP server: same DB file and schema, same API contract, and it serves the existing static UI.
3. Background or workflow worker: same task queue, workflow type names and schedule IDs, so it can replace the old worker in place.
4. Scrapers, pollers and shell runners.
5. Cutover: Dockerfiles, CI, image publishing, delete the old code, then the GitOps PR.

Rules:
- **The old code stays live until the cutover.** Each phase adds new code next to it and changes nothing deployed, which keeps every PR a two-way door.
- Open a tracking epic issue with these phases as a checklist. Each phase PR says "Part of #<epic>".
- Save the decision (scope, motivation, UI choice, epic, worktree/launcher paths) to Hindsight, so later sessions resume the right phase.
- **Read how components call each other before you split phases.** If one shells out to or imports another (for example the worker spawns the scraper per activity), put them in ONE phase. The caller can't be ported against a contract that doesn't exist yet.
- **Run independent phases in parallel.** Phases that don't import the logic library (worker/scraper) can start alongside phase 1. Phases that do (the HTTP server) wait until it merges. Use one worktree and branch per parallel phase.
- **Give every parallel prompt the same root manifest, word for word** (for example a Cargo `[workspace]` with `members = ["crates/*"]`, the same `rust-toolchain.toml` and edition). Tell each child which crates belong to the others. Then the second merge is a trivial rebase, not a conflict over the workspace root.
- **Cutover order:** don't plan a big-bang image swap. The user expects old and new to run side by side, and prefers a separate **beta stack**: its own namespace, DB (seeded from prod's backup), worker, Temporal namespace and `beta-<app>` hostname, while prod stays on the old build. A weighted in-prod canary is the alternative. Recipe for both: the `homelab-gitops-change-prs` skill, `references/canary-rollout.md`. Promote to prod only after the user has checked beta and every scheduled job has run once there. Say this plan before the cutover PR merges, because the release's automatic bump PR swaps prod images outright and must not be merged until beta checks out.
- **Keep the image names, ports, uid, probes, env vars and mount paths unchanged**, so the GitOps bump touches only `image:` lines. Distroless runtime images have no curl or python. Give the server binary a `healthcheck` subcommand and use it in the Dockerfile HEALTHCHECK.
- **Before you tell the user to merge the cutover PR, check it against the live manifests yourself.** Read `origin/main` of the GitOps repo (`git show origin/main:<path>`). List every `- name: <VAR>` in the env blocks and grep the new code for each one (`grep -rl '"VAR"' crates/*/src`). Then compare `runAsUser`, `readOnlyRootFilesystem`, the `mountPath`s and the probe paths. Don't rely on the child's "GitOps changes needed" list.
- **After the cutover merges, watch the whole release chain in a background script:** default-branch CI, then the release tag, then the image publish, then the GitOps bump PR appearing. Exit with a distinct code for each failure. Production changes only when the bump PR merges. Check its tags and digests before you tell the user to merge it.
- **Say the manual leftovers out loud.** Images that no manifest pins (for example a desktop docker-compose runner) don't update through GitOps. Give the user the exact rebuild command. Asked "do I need to change my local code?", answer the code question and the image question separately: the code is usually unchanged, but the running container stays on the old image until it's rebuilt.
- **Close-out checklist** when the user says "fully migrate and shut down the old one":
  - Confirm prod runs the new images (`kubectl get pods -o custom-columns=...image`, `/api/version`) with zero restarts.
  - `git ls-tree -r --name-only origin/<default> | grep -E '\.py$|\.mjs$|package.json|requirements'`, so no old-language code remains beyond what's kept by design (for example the browser UI and its tests).
  - `git grep -i '<old language>' -- README.md docs` for stale wording, then fix it in a `release:skip` docs PR.
  - Retire the beta stack (`canary-rollout.md` §4), close the epic, and save the end state to Hindsight.

## 2b. When the user says "do it all and merge"
That explicitly authorizes merging this effort's phase PRs, including the cutover, in that repo. Don't stop to ask between phases. Before each merge, run the gates yourself (fmt, lint, new tests, and the old suite) instead of trusting the child's report. Wait for CI with `gh pr checks <n> --watch`, because a plain `gh pr checks` exits non-zero while any job is pending. Note the authorization on the epic issue. Report briefly as each PR lands, and keep going to the next phase.

The user's word does not override a Hermes `approvals.deny` rule on `gh pr merge`. If the merge comes back BLOCKED by a deny rule, don't retry it in another form (`gh api`, the REST merge endpoint). Instead:
- Tell the user it's green and give two options: they merge, or you open a config PR that removes the rule. Hermes config deploys from the GitOps repo and restarts the pod, so that PR must not merge while children are running.
- Don't let the block stall the work, but **prefer splitting over stacking**. This user dislikes stacked PRs: a squash merge leaves the child conflicting, and deleting the base branch can close the child. First look for the part of the next phase that depends only on what is already on the default branch (for example CI cache plus images for components that already merged). Start that part from `origin/<default>` as its own PR, and leave the part that needs the unmerged phase for later. Stack (worktree from `origin/<phase-branch>`, PR against the default branch) only when nothing can be split off. Then tell the child its PR shows the earlier phase's commits until that phase merges.

## 3. Parity harness (put this in every phase prompt)
- Port the old tests and keep the test names recognisable.
- Add a **golden-fixture generator** in the OLD language (`scripts/gen_<crate>_golden.*`). It runs every public function over a broad corpus (test inputs, scraper fixtures, edge cases) and writes JSON. A new-language test replays every case. Commit the JSON. Unit tests miss tuned rules, and golden diffs catch them.
- If the port finds a bug in the old code, keep the old behaviour and list the bug in the PR. Fixing it mid-port breaks the parity check.
- Gate on the old suite too (for example `pytest` still green). That proves the phase touched nothing live.
- **HTTP server phase: add a contract-diff harness** (`scripts/contract_diff.*`). It seeds identical temp DBs, starts the old server and the new binary on two ports, fires a committed request corpus (every route, the test suite's requests, auth/no-auth, edge-case params, ingest batches built from fixtures) and diffs status, the headers that matter (CSP, cache, content-type) and JSON bodies, including key order where the UI relies on it. The bar is zero unexplained diffs.
- **Parity is not only bytes: gate on memory too.** A contract diff can show zero differences while the new server idles well above the old one's RSS and gets OOMKilled at a limit sized for the old process. In the HTTP-server phase prompt, require both servers to run on the same realistic data, and record `VmRSS`/`VmHWM` from `/proc/<pid>/status` at idle, after warm-up, and under a burst of the largest responses (`oha -z 30s -c 4 <biggest endpoint>`). Put the numbers in the PR. For a Rust/Tokio server, name the usual suspects up front: the glibc allocator (switch to jemalloc as `#[global_allocator]`), Tokio's default of 512 blocking threads (cap it, e.g. 16), a response cache sized differently from the old app's, and large bodies built several times over (value tree, string, gzip, cached copy). Tell the child to measure before it fixes anything and to keep response bytes and ETags identical.
  - **Include a cache-invalidating mixed load.** Run the large-body burst and the dashboard burst together, plus an empty write (for example `POST /api/ingest`) every 5 s, which bumps the data version so every cache entry goes cold and the warmers rerun. Steady read load alone hides the real peak: glibc grew past 2 GiB only under invalidation, while read-only bursts sat near 500 MiB.
  - **Untuned jemalloc isn't enough.** Defaults still peaked high. What worked was `narenas:4` plus `dirty_decay_ms:1000` (via the `tikv-jemallocator` config or `MALLOC_CONF`), together with the blocking-thread cap. That cut idle RSS about 10× with no throughput loss. `MALLOC_ARENA_MAX` on glibc helped far less.
  - Ask for a before/after table of VmRSS/VmHWM per phase (idle, warm-up, each burst, mixed load, idle after load) plus req/s, and a byte/ETag diff of every endpoint against the default-branch binary.
- **Real data for the diff:** run `kubectl auth can-i create pods/exec -n <ns>` before you write "copy the prod DB" into a prompt. Hermes' kubectl SA is usually read-only. If exec is denied, have the child pull real rows with read-only GETs from the in-cluster Service (`http://<svc>.<ns>.svc:<port>/api/...`) and load them into fresh DBs for both servers. Keep the data in scratch, never commit it, and never send writes to the live API.

## 4. Python → Rust gotchas to name in the prompt
- `regex` has no lookaround or backrefs. Use `fancy-regex` only where needed.
- Python's `round()` is round-half-even. Also watch `\b`/`\d` Unicode semantics, case-folding, float formatting, dict insertion order, and naive vs aware datetimes.
- Port `sqlite3` code to `rusqlite` with the `bundled` feature, and test against an in-memory DB with the same schema.
- Turn on serde_json's `float_roundtrip` feature. The default float parser can be off by one last digit against Python's `json`.
- Emoji and other symbol characters next to `\b` behave differently in Rust `regex` than in Python `re` (for example "✔️32GB" loses its RAM match). Golden fixtures with real listing titles catch this.
- If the old code hashes its own source or data files (a rules or config version), port the hash byte for byte, so values stored by either side stay valid. Then any edit to the old file fails the new golden tests until the generator is re-run.

## 5. Launch
Follow the SKILL.md hand-off recipe: a worktree per phase, the toolchain pre-installed, prompt.md + run.sh in a scratch dir, background run with notify. Use `--model opus --effort high` and `--max-turns` in the hundreds for a port phase. Allow the build tool, the old-language test runner, git and `gh pr create`, and disallow `gh pr merge` and pushes to the default branch. Children never merge, even when the user authorized merging; the parent merges after its own gate run. Clone the first phase's run.sh for the next phase with `sed` on its paths, and widen `--allowedTools` only for what that phase needs (for example `curl` and `node` to compare against the old scraper).

## 6. Driving several phases with one background script
Use one `drive.sh` (launched with `background=true, notify=true, persist_on_release=true`) when phases must run unattended: per phase, create the worktree, run the child, check that a PR exists, resume the child if not, then loop on CI. Rules:
- **Look for other tabs' work before you launch.** Desktop tabs share the workspace but not the conversation, so another tab may already be running a phase. Check `git worktree list`, `ls /opt/data/cache/scratch | grep <repo>`, `gh pr list --search "Part of #<epic>" --state all` and `ps -eo pid,etime,args | grep '[c]laude -p'`. Resume or rebase what exists. Never start a duplicate phase.
- **Make every `cd` fatal:** `cd "$wt" || exit 1`, and check `readlink /proc/<child-pid>/cwd` after launch. `git worktree add -b <branch>` fails when the branch already exists locally, for example in another tab's worktree. A failed `cd` without `|| exit` then starts the child in the main checkout.
- **Kill only the PIDs you started.** Stop a driver with `kill <driver-pid> <child-pid>`, and look up the PIDs with `ps -o pid,ppid`. Never use `pkill -f`. To list children, use `pgrep -x claude` plus `readlink /proc/<pid>/cwd`. `pgrep -f 'claude -p'` also matches your own shell, because its command line contains the pattern. Don't edit a script while bash is running it, because bash reads it incrementally. Write `drive2.sh` instead. To change a later phase of a running driver, edit that phase's prompt file instead. The driver only reads the prompt when the phase starts, so that edit is safe.
- **Exit 0 and `subtype: success` don't mean the work is done.** Read the end of `.result`. A child cut off by the usage limit ("You've hit your 5-hour limit · resets …") still reports success, with the work left uncommitted in its worktree. After the reset, resume it with `--resume <session_id>` from the same cwd, because sessions are looked up per directory. Tell it what changed in the meantime (which base merged, which PRs exist).
- **Stacked branch after its base squash-merges:** the child PR turns `CONFLICTING`. Have the driver check `gh pr view <n> --json mergeable` before it waits on CI. Resume the child to rebase onto `origin/<default>` (identical patches drop out), rerun the gates and `git push --force-with-lease`. Have it keep a `backup/<branch>-pre-rebase` branch, and delete that branch once CI is green.
- **Base PR merges while a fix child still runs on that branch:** the child would push to a merged branch and edit a closed PR. Kill the `claude` process itself, not only its bash wrapper (find it with `ps -eo pid,comm,args | grep '[<session-id-fragment>]'`, because killing the `process_manage` wrapper can leave the child running). In the same worktree, `git checkout -b <new-fix-branch> origin/<default>`; uncommitted edits carry over. Resume the same `session_id` with a prompt that names the new branch and asks for a new PR.
- **Trivial conflict on a branch whose child is still editing:** you can resolve it in place when the child's uncommitted files don't overlap the conflict. Run `git merge --no-commit origin/<default>`, fix the conflicted file, `git add` only that file, commit the merge and push. The child's unstaged edits stay untouched. Run the cheap gate for the touched file (e.g. node tests) before you push.
- **CI loop:** `gh pr checks <n> --watch --interval 30`, then up to 4 rounds of resuming the child to fix the failures with "don't weaken or skip tests", then stop and report.
- **Release labels:** if the repo auto-releases on merge based on a PR label, label phases that deploy nothing as skip before they merge, and label only the cutover PR with a real bump. A missing label means a pointless release plus a GitOps bump PR. If you add the label right after the merge, it still counts as long as the release workflow hasn't read it yet.
- **Status reports:** when the user asks where things stand, answer with one table (phase | PR | status), then the single next action that is theirs. Mark which merge actually changes production.
- **Look up the child's PR with `gh pr list --head <branch> --state all`** in a launcher's final step. The user often merges while the launcher is still waiting, so an open-only lookup returns nothing and the script exits non-zero after a success. Read the child's `.result` before you treat that exit code as a failure.
- **When the user says "merged", verify it** with `gh pr view <n> --json state,mergedAt,headRefOid`. Check that the merged head is the green, rebased SHA. Then check that master CI passed.
