# Hermes setup audit ("is my Hermes set up well?")

Use when the user asks to audit, health-check or clean up their Hermes: memory, Hindsight, sessions, usage/cost, tools, skills. Gather everything read-only first, fix only the safe in-scope item (built-in memory dedupe), then report and ask before anything destructive.

## Procedure (batch the reads in parallel)

1. **Find the CLI and host.** `hostname`; the `hermes` binary may not be on PATH in container installs — try `/opt/hermes/bin/hermes` (`export PATH=/opt/hermes/bin:$PATH`).
2. **Health:** Run `hermes doctor` with a bounded timeout and save the full output under `$TMPDIR`; capture its actual exit status rather than a following command's status. If a short run times out, retry once with a longer bound (for example, `timeout 540 <resolved-hermes-cli> doctor`) before calling it hung. Inspect the complete report and separate optional, unconfigured integrations from intended capabilities. Test warnings for intended capabilities with a small read-only call through the active tool runtime; a working runtime call disproves a blanket outage claim but does not establish why the CLI check disagrees. Do not run `doctor --fix` just to silence warnings.
3. **Usage/cost:** `hermes insights --days 7` gives platforms, top tools, top skills, activity, notable sessions. For model/day/cost splits query `state.db` read-only (`sqlite3.connect('file:$HERMES_HOME/state.db?mode=ro', uri=True)`), table `sessions`: `model, source, message_count, tool_call_count, input_tokens, cache_read_tokens, estimated_cost_usd, billing_provider, billing_mode, cost_status, end_reason, started_at` (unix epoch). `cost_status='estimated'` behind a proxy (LiteLLM) or subscription is not a real bill — say so.
   - `end_reason='startup_orphan_reap'` counts sessions killed by gateway/pod restarts.
   - Sessions with 300+ messages are the coaching signal: start fresh per topic, `/compress`, `/usage`.
4. **Sessions:** `hermes sessions stats`, `hermes sessions list --limit 100`, `hermes config get sessions` (auto_archive / auto_prune / retention). Under ~100 sessions / <100 MB is healthy — recommend no deletion; `hermes sessions prune|archive` only on explicit yes.
5. **Cron:** `hermes cron list` — check each job's last run/error.
6. **Skills:** `hermes curator status` (consolidate on/off, unmanaged count), skill count via `find $HERMES_HOME/skills -name SKILL.md | wc -l`, compare with distinct skills loaded in insights.
7. **Config spot-checks:** `hermes config get web|compression|curator|delegation|sessions`. Empty `web.extract_backend` with a search-only search backend means `web_extract` fails — recommend a real extract backend. Empty `delegation.model` means subagents/kanban workers run on the main (often most expensive) model.
8. **Hindsight:** `GET <api>/v1/default/banks/<bank>/stats` and `.../operations?status=processing` / `?status=failed`. Old `last_consolidated_at` + large `pending_consolidation` = stalled; see the Hindsight section of `references/troubleshooting.md` for the fix. Repeated near-identical facts in recalled context are the user-visible symptom (consolidation is what dedupes). Report the backlog size and the DB's memory limit together, because releasing a big backlog can take the database down.
9. **Built-in memory:** read usage from the system-prompt header; dedupe overlapping entries (see pitfall below).
10. **Disk:** Measure cache directories with `du` and filesystem usage with `df`, then inspect stale worktrees/clones in the workspace. Age or a cache-like name alone does not establish that deletion is safe. Before approved deletion, resolve each exact path, inspect its contents for regenerable build output versus source, and check running jobs and references to external build targets; a process-name search alone can miss a compiler using `CARGO_TARGET_DIR`. Delete only the approved artifacts, verify the paths are gone, and compare filesystem usage afterward. Keep package caches unless they are in scope; they can make repeated installs faster. Classify each repo dir in one loop: branch, `git status --porcelain` count, `git log @{u}..HEAD` count, and `gh pr list -R <repo> --head <branch> --state all --json state`. Remove only MERGED + clean + nothing unpushed (`git worktree remove <dir>` for worktrees, `rm -rf` for clones, then `git worktree prune` in each main repo). A detached HEAD is safe when `git branch -r --contains HEAD` lists `origin/main`. Keep main checkouts, open-PR dirs and anything with untracked files; `cargo clean` an open PR's `target/` instead (often the biggest win, it rebuilds).
11. **Best-practice docs:** per-page `.md` URLs 404. Fetch `https://hermes-agent.nousresearch.com/docs/llms-full.txt` and slice by page title (`t.find('# Tips & Best Practices')`, `'# Troubleshooting: "My Agent Feels Dumber"'`).

## Verify usage claims before publishing recommendations

1. Discover the SQLite schema before querying it. Open the database read-only, resolve `$HERMES_HOME` in Python or the shell, and keep one explicit time window and source filter for each metric.
2. Distinguish sessions, worker runs, delegate tool calls and individual delegated tasks. A single call can launch several tasks; never compare these counts as the same denominator. State the unit next to each number.
3. Aggregate skill loads from tool-call records rather than keyword mentions. Label user-message keyword counts as mentions only, because pasted briefs and repeated context can inflate them. Read representative transcripts to understand how the skill was used.
4. Separate current config from historical behavior. A newly changed default does not explain old route choices; compare routing before and after the change before calling a rule ineffective.
5. Report actual charges, estimated API-equivalent cost and subscription-included usage separately. Do not sum `COALESCE(actual_cost_usd, estimated_cost_usd)` and label the result spend, or infer that all historical usage was subscription-covered from today's credentials.
6. Count installed skills and runtime-visible skills separately, including bundled copies and shadowing. Inspect the loader before claiming a metadata field is ignored; a narrow search with no match is not proof. Label description-length token calculations as estimates unless measured with the actual tokenizer and rendered prompt.
7. Re-check mutable facts such as memory fullness, cron jobs and model defaults immediately before publication. Do not freeze stale values into a guide or infer that infrequently loaded skills should be disabled automatically.
8. Preserve the bounded aggregate output and queries used for the report, excluding credentials and private message samples. Reconcile every published total programmatically before opening the docs PR.

## Skill pruning and leaderboard reviews

1. Confirm the requested scope and explicit keeps before generating a deny-list. Preserve mobile/Expo, React/React Native and browser workflows for episodic app work; inspect dependencies between skills rather than disabling every skill without recent loads.
2. Use a bounded read-only session query with the same time window and source filters for loads and total calls. Parse both JSON-string and object tool arguments, normalize qualified skill names, and reconcile installed names against runtime-visible names. Label the result "not observed in the sampled history", not "never used".
3. Estimate removable prompt tokens from the rendered skill index with the model's tokenizer when available. Multiply by matching model requests, not assistant-message count: tool continuations, retries and compression make those different units. Inspect cache-read/write usage and historical billing modes before estimating cost; do not claim all tokens were cached or subscription-covered from current config alone.
4. Compare candidates with retained workflows before proposing additions. Fetch the actual upstream SKILL.md, supporting scripts, license and maintenance state; a leaderboard description or star count does not establish safety, usefulness or Hermes compatibility. Trial a focused skill against a real task rather than importing another broad pack.
5. For recent best practices, read the official Nous blog and upstream release notes, then compare with the running commit. Release notes can aggregate older patch changes; do not promise that a newly tagged release fixes a live issue without checking the relevant change and deployment.
6. Implement approved pruning with the documented `skills.disabled` setting in the configuration owner's repository. Keep files installed, describe how to re-enable them, validate with Hermes's config loader, and verify the PR's exact diff and checks before claiming readiness. Keep an upgrade separate from skill cleanup unless both were approved.
7. Verify pruning from structured loader output or full canonical identifiers, not a formatted skills table. Compare the configured deny-list, installed inventory and runtime-visible inventory as sets; account for platform eligibility, bundled copies and shadowing. Treat clipped names as display artifacts, not rename candidates. If the counts still disagree, report the discrepancy as unresolved instead of guessing that platform filters explain it.
8. Check retained skills for renamed or removed tool APIs after version changes. Update stale instructions where practical instead of assuming disabling the skill fixes the underlying compatibility problem.

## Report shape

Lead with the single biggest problem. Then: done already → numbered problems (one line each, plain English) → what's healthy → 3–4 coaching tips tied to their actual numbers → a numbered "say go and I'll" list, with the open decision (e.g. which web extract backend) as explicit options. Where config.yaml is seeded from Git on pod start, config fixes go via PR to that repo, not `hermes config set`. Check the main-model auth before quoting cost: a Claude Code OAuth/subscription token means the dollar figure is quota, not spend. Before proposing any resilience or tuning fix, search upstream docs and issues for how others solved it and confirm the setting exists in the installed version; the user expects researched fixes, not plausible guesses.

Validate a config.yaml edit for a Git-seeded install without pyyaml: copy it into a temp dir and run `HERMES_HOME=<tmp> hermes config get <key>`, which parses it with Hermes's own loader.

## Keeping it current ("how will I know about upgrades?")

First check what already tracks the base image (Renovate config and its Dependency Dashboard issue in the image repo, its schedule and grouping) and the running vs latest release (`hermes --version`, `gh release list -R NousResearch/hermes-agent -L 5`). Renovate covers "a release exists" weekly. It doesn't cover "has the fix for my bug shipped". Fill that gap with `templates/upstream-watch.py`, a `no_agent` daily cron that diffs releases and watched upstream PRs and comments on a GitHub tracking issue for phone notifications. Test it with `HERMES_HOME=<tmp> python3 upstream-watch.py --no-comment` twice (the second run must be silent), test `report()` with a faked newer release, then run it once for real to set the baseline, and fire it once through `cronjob(action='run')` to prove the scheduler environment has `gh`/`kubectl` auth.

## Pitfalls

- **Memory batch removes match by substring across ALL entries.** Pick an `old_text` that occurs only in the target entry, and check `removed_entries` in the response — a phrase shared with another entry silently deletes the wrong one. Re-add anything lost immediately.
- Merge duplicate memory entries into fewer, denser ones that keep every fact; don't just delete repeats.
- Don't delete sessions, Hindsight ops, or caches during the audit itself — list them and wait for a yes.
- After any fix that restarts background work (cancelling a stuck op, raising a limit), watch the dependent pods for a few minutes (`kubectl get pods`, Prometheus CPU/memory/fs-read for the namespace) before reporting it fixed.
