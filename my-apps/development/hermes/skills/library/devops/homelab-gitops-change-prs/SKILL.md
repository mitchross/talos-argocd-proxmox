# Homelab GitOps change PRs

## When to Use
Any change to `mitchross/talos-argocd-proxmox` shipped as a PR: app manifests, RBAC, Helm values, Omni template, Hermes's own deployment/config. Live-only diagnosis without a Git change: `homelab-triage` / `homelab-ops`.

Check what the pod can do before handing a command to the user: `kubectl auth can-i <verb> <resource> -n <ns>` (subresources need `--subresource`: `kubectl auth can-i create pods --subresource=exec -n <ns>`; `can-i create pods/exec` wrongly answers no) and `talosctl -n <node> version --short` (talosctl/omnictl authenticate through the Omni service-account env when it is set). Run what you are allowed to; hand only the rest to the user as an exact command. Hermes's own permissions live in this repo (`my-apps/development/hermes/rbac.yaml`, plus its `CLAUDE.md` and the `homelab-ops` skill, which must be updated in the same PR); homelab-images only ships the binaries. The Hermes kustomization sets `namespace: hermes`, and JSON patches run before the namespace transformer, so a Role/RoleBinding for another namespace can't live there. Put it in the app that owns that namespace (e.g. `infrastructure/networking/cilium/hermes-config-reader.yaml` for `kube-system`), and confirm with `kustomize build | grep -A3 <name>` that it renders in the right namespace. `hermes-viewer` reads no ConfigMaps or Secrets, so grant single ConfigMaps by `resourceNames`.

`talosctl list/read` on `/var/lib/kubelet/pods/<podUID>/volumes/...` reads a pod's emptyDir or mounted files from the node side when exec is not allowed.

## vLLM image and checkpoint changes
Retain rollback manifests and map `model-manifest.json=<new-manifest>.json` in the ConfigMap generator so download/sync/wait consumers share the new pin without pruning old weights. Bake community site-packages patches into a digest-pinned homelab-images base; CPU import/patch smoke is separate from post-merge GPU, vision and KV-capacity acceptance.

## Commands handed to the user
- Before asking the user to create any credential, grep the repo's ExternalSecrets (`git grep -n -A3 remoteRef origin/main -- '*secret*.yaml'`) for an existing one that fits and reuse it. Say plainly what that token's scope allows. The user refuses to make a new token when one exists.
- Give exact copy-paste commands, not click-through steps. The desktop shell is zsh with the 1Password `op` CLI: write hidden prompts as `read -rs "T?Token: "` (bash's `read -p` means coprocess in zsh and leaves the variable empty, so `op item edit` saves a blank field). Write secrets with `op item edit <item> --vault homelab-prod "<field>[password]=$T"`.
- Never write `Bearer $(...)` or `Bearer <token>` in a chat reply: the display masks it as `***` and the copied command breaks. Read the secret into a variable and use `curl --oauth2-bearer "$CF"`. Add a length check (`echo ${#CF}`) so an empty secret shows up as 0, not as a `null` API reply.

## Workflow
1. `git fetch`, then `git worktree add ~/.local/share/agent-worktrees/talos-argocd-proxmox/<topic> -b <branch> origin/main` (the shared Git workflow block in every repo's AGENTS.md and dotfiles; not `../wt-<topic>` siblings). Never edit the main checkout (it may sit on someone's branch). Reuse the task's worktree for CI fixes; once the PR is merged or closed, `git worktree remove <path>` if it is clean and its HEAD equals the PR's `headRefOid` (squash merges show `[gone]` upstream and `ahead 1`; that is not lost work). Before pushing to an existing PR branch, `git fetch` it: Mitch or a desktop agent may have pushed (e.g. a main merge) meanwhile; rebase your local commit onto it, never force-push. If fetch fails with empty or corrupt objects, don't repair the shared checkout mid-task; `git clone --depth 50 https://github.com/mitchross/talos-argocd-proxmox ~/.local/share/agent-worktrees/talos-argocd-proxmox/<topic>` and branch there. Don't put worktrees on a clone under `$TMPDIR` (pruned after 24 h idle). Tell the user it's broken. Repair it only when they ask, using `references/shared-checkout-repair.md`.
2. Read root `CLAUDE.md` plus each nested `CLAUDE.md` on the path before editing.
3. Verify against live state first (kubectl get; in-cluster Prometheus at `http://kube-prometheus-stack-prometheus.prometheus-stack.svc:9090` needs no auth). Git is desired state, the cluster is truth for sizing/placement.
   For reliability, resilience or tuning changes to a third-party app (Hindsight, Hermes, LiteLLM, Postgres), and before adding any new component (exporter, sidecar, plugin, pipeline), search upstream docs, the app's plugin catalog and issues for how others solved it *before* designing the fix. Present the native/catalog option next to the custom one with a one-line trade-off each, then recommend one; the user otherwise stops the work to ask whether it is the right approach. Then confirm each env var or flag exists in the pinned tag's source: `git clone --depth 1 --branch <tag> --filter=blob:none <repo>` into `$TMPDIR` and grep it, or grep inside the running pod. The user asks for this explicitly, and a plausible knob can be inert (e.g. a drain timeout overridden by the container init's own kill timer). Cite the doc or issue in the PR body.
4. Commit only task files. Check `git status` and `git show --stat` before pushing: a failed `cd` inside a chained command writes files into the worktree root and `git add -A` commits them.
5. Open the PR with a short plain-English body (what changed, a small table at most, what could not be checked, rollback). Merge only when the user names that PR; "finish X, merge" covers PRs already for X, not new destructive ones.
6. Wait 60-90 s, then `gh pr checks <n>`; read failures with `gh run view <id> --log-failed`. If it says `no checks reported` after a push, check `gh api repos/<o>/<r>/pulls/<n> --jq .mergeable_state`: `dirty` means a merge conflict, and GitHub runs no workflows until you `git merge --no-edit origin/main`, resolve, and push (never force-push). Hermes `config/config.yaml` conflicts often, because the config migrator's pinned keys get appended at the end; keep both blocks.
7. No pyyaml in the pod: `python3 -m venv $TMPDIR/venv && venv/bin/pip install pyyaml pytest` for local validation. To just parse the Hermes config, `/opt/hermes/.venv/bin/python` already has `ruamel.yaml` (`ruamel.yaml.YAML(typ='safe').load(...)`). For Helm-backed apps, put Helm and Kustomize at the CI pins (`cluster-ci.yml` `env:`) into `/opt/data/tools/bin` and source `/opt/data/tools/talos-env.sh`; plain `kubectl kustomize` can't inflate charts. Run repo validators in `scripts/` (e.g. `validate-omni-contract.py`, tests in `scripts/tests/`). `validate-kopiur-coverage.py` and `validate-vpa-policies.py` take a rendered file: `kubectl kustomize <dir> > r.yaml && venv/bin/python scripts/<v>.py r.yaml`. Fed one app's render, `validate-vpa-policies.py` also prints `stale VPA coverage exemption` for every other app's exemption; ignore those and check only your own objects in the summary line. Run `gitops-risk-check.py` with the venv python after sourcing `talos-env.sh`, because it shells out to `kustomize` and fails as `check-failed` without it on PATH.

## New apps and shared services
- Split a multi-part feature into one PR per layer, in dependency order (shared helper → consumer app → model backend → glue/skill). Tell the user the sequence up front and ship PR 1 without waiting for another go-ahead.
- Before offering a fix in chat, grep the pinned tag for the knob and check live logs that the hypothesis fits; say so plainly when the plan has to change.
- Before claiming a root cause or its start date, recall Hindsight for the same symptom. An earlier incident or a closed fix PR changes the story, and a wrong "this started with X" claim gets corrected by the user. When Hermes lacks a permission that keeps a diagnosis going back to the user, propose a scoped grant through a PR (an Argo account or RBAC verb), saying what it can and can't do.
- After merge, wait for ArgoCD to reach the merge commit (~5 min) before calling anything missing, then run one real end-to-end test and report measured numbers.
- Depth (probing existing consumers, IP-only settings and pinned clusterIPs, shared SMB folders across namespaces, gosu entrypoints on SMB, reusing a pinned image as a script runtime, mock-server tests, post-merge rollout checks): `references/new-apps-and-shared-services.md`. iGPU/NPU placement: `references/accelerator-placement.md`.

## Pitfalls
- The `static-risk` CI gate BLOCKs any change that makes an ArgoCD Application disappear (deleting an app directory). To retire an app, keep the directory with only `namespace.yaml` in its kustomization so resources prune but the Application stays; delete the shell later after checking live.
  - Cluster CI's render job also fails any non-Component kustomization that renders zero objects, so `resources: []` is not an option. When the namespace is owned by another App (`FailOnSharedResource=true`) or no namespace fits, render one placeholder ConfigMap (e.g. `<app>-retired`) instead.
  - Root-managed `custom-entrypoints/*-app.yaml` Applications carry no resources finalizer, so deleting the Application orphans its resources rather than pruning them. Always prune first through the shell, check live that the app manages only the placeholder (`status.resources`), then delete the Application, its kustomization line and any AppSet exclude in a follow-up PR.
  - That follow-up shows `BLOCK application-disappears` by design. `main`'s protection doesn't require the check; say in the PR body that preservation was verified live.
  - Preview the gate before pushing with `python3 scripts/gitops-risk-check.py --no-fetch --format text`. It compares committed HEAD, so commit first.
- `static-risk` failing with `check-failed` / `git failed:` and an empty message (read it from the run's `gitops-risk` artifact or the "Show report" step) is not a finding: the checker runs `git merge-base --is-ancestor origin/main HEAD`, which fails silently when the branch is behind main. Fix with `git fetch origin main && git merge --no-edit origin/main && git push` (no force-push needed); re-running the job alone does not help.
- Helm values `metricRelabelings` (kubelet, cAdvisor, apiserver, kube-state-metrics) REPLACE chart defaults. Copy the live defaults (from `/api/v1/status/config`) in first, then append.
- **Omni template edits, node resets/syncs and Longhorn settings:** load `references/omni-longhorn-node-changes.md` first. Always-on: list every pod on an affected node (Hermes itself may be there on a 1-replica volume) and make replica raises a prerequisite; quote node capacity only from live `kubectl get nodes`/`top`; trust `omnictl cluster template diff` over pyyaml/CI.
- Widening an RBAC role: say plainly in the PR what the new verbs reach (`pods/exec` exposes secrets mounted in containers; `patch` on Deployments/nodes needed for restart/scale/cordon also allows any field edit, and Argo self-heal reverts app drift but not node changes). Keep secrets and create/edit of app resources out.
- Image bump PRs: take each `tag@digest` from the release run's own output (annotations or summary), not from a predicted tag. Confirm it against the registry: a `HEAD` on `/v2/<owner>/<image>/manifests/<tag>`, with an OCI-index `Accept` header and an anonymous `ghcr.io/token`, gives `Docker-Content-Digest`. Bump every repeated ref of an image in the same PR, because a half-bumped app splits pools across builds. Then `kubectl kustomize <app dir>` and count that no ref is left on an old tag. Bump a sibling image (e.g. web) only if its source changed since the pinned tag.
- Pinning a mutable tag (`main@digest`, `latest@digest`) to semver: list the registry's version tags, then compare the index digest or the image config's `org.opencontainers.image.revision` label of `main` and the newest release tag. When they share the commit, the pin changes no code on rollout; say so in the PR. Leave images that publish no version tags (only `main`/`git-<sha>`) on `tag@digest` and say why. Delete commented-out manifests that hold the only unpinned copy.
- **Argo CD prerelease bumps, Temporal namespace retention, Cilium agent flags:** `references/component-knobs.md` (CRD diff + CI tool pins for Argo; retention is create-time only for Temporal; Cilium agents don't restart on config changes, so say so in the PR).
- Risky image swaps (rewrites, major upgrades): propose running old and new side by side, not a straight image bump. The user expects that from Kubernetes, and prefers a separate beta stack (`<app>-beta` namespace, own DB seeded from prod's kopiur snapshot, own Temporal namespace, `beta-<app>.vanillax.me`) over an in-prod weighted canary. Argo here ignores HTTPRoute `backendRefs[].weight`, so weight edits don't reach live through a sync. Recipe and safety checks: `references/canary-rollout.md`.
- **A merged edit that Argo "applies" but live never changes** (app OutOfSync, `serverside-applied` loop, `generation` frozen): load the "synced edit never reaches live" section of `references/component-knobs.md`. Always-on: never put an ignoreDifferences path inside a CRD list; spell out the API default in Git instead. Before adding any ignore rule, ask why server-side diff is off. Mitch expects "sync all" to be safe, so a selective sync or a resource rename is a diagnostic, never the fix. Call a cause a hypothesis until a live check after the fix proves it, and say so in the PR body.
- Monitoring/visibility asks ("hard to read the reports", "I only care what's happening now"): answer with a Grafana dashboard in the repo's Start Here folder, not a new site, Alertmanager's UI, or more digest text. Recipe: `references/grafana-dashboards.md`.
- The user often merges PRs while you work, sometimes within minutes of opening them: re-check `gh pr view <n> --json state` before reporting status AND before pushing any follow-up commit (a CI fix, a merge of main). Commits pushed after the merge land on a dead branch and never reach `main`; if the fix is still needed, open a new PR from fresh `origin/main`.
- Never give a helper sidecar (exporter, gc loop) a readiness probe in a pod that serves a route: pod readiness is all containers, so a failing sidecar drops the pod from the Service and takes the app's route down. Let it crash-restart on its own instead.
- Hermes pod env lives in `my-apps/development/hermes/deployment.yaml`. When the browser tool's Chromium dies with "No usable sandbox", set `AGENT_BROWSER_ARGS=--no-sandbox,--disable-dev-shm-usage` there. Hermes injects that flag only under Docker or root, and the pod runs as uid 10000. Prove the fix first from the Hermes terminal with `$AGENT_BROWSER_EXECUTABLE_PATH --headless=new --no-sandbox --disable-dev-shm-usage --dump-dom <url>`. Merging restarts Hermes, so sequence it after anything that's running.
- **Keep Hermes's own toolset in Git** so a rebuild comes back complete: whenever a skill, MCP server or plugin is added, open a PR in the same session. Exact files per kind (external-skills.txt, skills/library, `mcp_servers` + ExternalSecret, seed.sh plugin loop + `plugins.enabled`) and how to prove the seed change: `references/hermes-toolset-in-git.md`.
- Head series stay high for hours after adding drop filters (old series sit in the head block until compaction). Verify with `count(<dropped_metric>)` returning none, not total head series.
- Before releasing a stuck queue or backlog on a stateful app (cancelling a dead job, unpausing workers), measure the backlog and the database's memory limit. A large backlog runs all at once, fills a small Postgres limit, and slows `pg_isready` past a 3 s probe timeout, so the liveness probe kills the busy DB in a loop and the app crash-loops on its startup migration. Put DB headroom (memory limit, probe `timeoutSeconds` ~10, liveness `failureThreshold` ~6) in a PR first, or watch per-pod CPU, memory and `container_fs_reads_bytes_total` in Prometheus right after. Diagnose a crash loop from `kubectl describe` (Last State exit 137 + probe-failure events = probe kill, not OOM) and `kubectl logs --previous`.
- Single-replica apps whose worker identity defaults to the pod hostname strand in-flight jobs on every restart. Pin a fixed worker id via env and roll out one pod at a time so two pods never hold the same id.
- CronJob failure history keeps `KubeJobFailed` firing after later runs succeed. Add `ttlSecondsAfterFinished` (e.g. 2 days) to the jobTemplate. Longhorn-generated recurring-job CronJobs can't take it, so delete their stale failed Job once by hand.
- Never switch an existing Argo-managed Deployment from `RollingUpdate` to `Recreate`: the API server defaulted `strategy.rollingUpdate`, no field manager owns it, so server-side apply can't clear it (`rollingUpdate: null` doesn't help either) and the sync fails with "rollingUpdate: Forbidden". Use `type: RollingUpdate` with `maxSurge: 0, maxUnavailable: 1` instead (same one-pod-at-a-time effect on 1 replica). Prove any strategy or immutable-field change before the PR with `kubectl kustomize <dir>`, extract the Deployment, then `kubectl apply --server-side --dry-run=server --field-manager=argocd-controller -f <file>` against live. After merge, check `kubectl -n argocd get application <app> -o jsonpath='{.status.operationState.message}'`, because one failing resource leaves the rest of the PR live and the app quietly OutOfSync.
