# Ponytail Audit to PR

This skill runs a read-only Ponytail audit of a repo as a Kanban swarm: parallel auditors → a verifier with `ponytail-review` → a synthesizer that writes the report. It turns the verified report into a `to-tickets` epic, with issues for every Must item plus any the user names. Then it hands the spelled-out fixes to Claude Code on `claude-sonnet-5-5` as ONE PR with real test output. It **never merges**, and it leaves design questions as issues for the user. It needs the Hermes pod tools: `/opt/hermes`, `gh`, `claude`, and Kanban.

## When to Use
- "Run a Ponytail audit as a swarm" / "Kanban swarm audit of <repo>"
- "Turn the audit into an epic with a checklist and issues for X, Y"
- "Hand C1, F2, B1 to Claude Code as one PR that closes them"
- "The restart killed the fix run, resume it"
- "Hermes restarted and the audit cards are stuck in running"

## Prerequisites
- The repo is cloned under `/opt/data/workspace/<repo>`, and `gh` is logged in with push access.
- Skills: `ponytail-audit`, `ponytail-debt`, `ponytail-review`, `humanizer`, `to-tickets`, `pr`, `claude-code`. For swarm internals, also load `hermes-agent` (`references/background-systems.md` and `templates/kanban-swarm.py`).
- Toolchains the repo's gates need, installed on the PVC because system dirs are read-only (see Procedure step 7). For radar-ng the env file is `/opt/data/tools/radar-env.sh`.

## How to Run
Invoke everything through the `terminal` tool. `hermes` is not on PATH, so use `/opt/hermes/bin/hermes`. Python with Hermes modules is `/opt/hermes/.venv/bin/python`. Wrap long or complex commands in a script file (`write_file`) and run `bash script.sh`. Inline pipelines in background calls get blocked waiting for an approval prompt.

## Quick Reference
- Board: `/opt/hermes/bin/hermes kanban ls`, `... kanban show <id>`, `... kanban diag`
- Stuck cards: `/opt/hermes/bin/hermes kanban ls --status running`
- Reclaim an orphan: `/opt/hermes/bin/hermes kanban reclaim <id> --reason "pod restart"`
- Swarm with full card bodies: copy the `hermes-agent` template `templates/kanban-swarm.py`, then run `cd /opt/hermes && /opt/hermes/.venv/bin/python <copy>.py`
- File issues: `scripts/file_audit_issues.py` (this skill)
- npm + Python repo gates (deal-scout layout), one at a time with logs and counts: `scripts/run_npm_py_gates.sh <worktree> <logdir> [env-file]` (this skill)
- Tick merged findings on the epic: `scripts/tick_epic.sh <o>/<r> <epic> <ID>...` (this skill)
- Fix run: `scripts/run_claude_fix.sh` + `templates/fix-prompt.md` (this skill)
- Model-pinned read-only auditors in parallel: `scripts/run_claude_audit.sh <brief-dir> H:claude-sonnet-5-5 P:claude-sonnet-5-5 ...` (this skill)
- GitOps/Kubernetes repo audits (talos-argocd-proxmox): area split, checks that find real bugs, render tools: `references/gitops-repo-audit.md` (this skill)
- CI/native gate on a PR branch: `references/ci-and-native-verification.md` (this skill); it also has the "CI build speed (Rust)" recipe for checking cache hits and fixing cold in-Docker compiles
- radar-ng backend deploy after a merge: background `scripts/bump_radar_backend.sh <ghcr-backend run> <ci-rust run> <merge sha> <PR>` waits for the release and opens the talos bump PR (this skill)
- radar-ng web deploy after a merge that touched `web/`: background `scripts/bump_radar_web.sh <ghcr-web run> <merge sha> <PR> <notes.md>` (notes = one markdown bullet per user-visible change)
- Parallel batches: run 2 at once only when their file sets don't overlap; each PR targets master (never stack). Name the other batch's files as off-limits in the prompt and drop cargo/jest to -j 2 / --maxWorkers=2 so two gate runs fit the pod.
- Before filing a batch, check for prior work from another chat tab: `gh issue list --search "<ID>: in:title"`, `git branch --list '*<ids>*'`, and an existing `claude-ponytail-batch<N>.md`. Reuse them instead of filing duplicates.
- radar-ng AGENTS.md (since 2026-10-31): create worktrees only under `~/.local/share/agent-worktrees/<repo>/<task>/` (not sibling folders), remove merged ones with plain `git worktree remove <path>` (never `--force`), and keep any worktree that has unpushed work.
- Never `pkill -f <pattern>` from the terminal tool: the pattern is in the calling shell's own argv, so it kills the tool call (and any matching background run). Find the PID with `ps -eo pid,args | grep`, then `kill <pid>`.
- In PR bodies, never write "does not close #N" / "fix #N" in prose: GitHub parses the keyword and closes it anyway. Check `closingIssuesReferences` after opening.
- radar-ng TestFlight: `gh workflow run build-ios.yml -R mitchross/radar-ng --ref master -f scheme=radarng -f testflight=true`; the Mac runner sleeps, so check `actions/runners` and tell the user `launchctl kickstart -k gui/$(id -u)/actions.runner.mitchross-radar-ng.mac-ios` if offline. To confirm the upload, grep the log for `UPLOAD SUCCEEDED|Delivery UUID|Failed to upload`. If the run is red but shows `UPLOAD SUCCEEDED`, the build was delivered: read which step failed before calling it a failure. A bare `ERROR` grep matches Xcode build-setting lines (`..._ERROR`) and harmless altool lines, which buries the result. If the user says CarPlay vanished, check the preflight's `CarPlay build:` line (see the CI/native reference). `build-ios.yml` has a `carplay` input that defaults on. Apple's carplay-maps grant also covers TestFlight signing. The Watch app and widget are in every build: if the Watch app is missing, it's the iPhone Watch app → Available Apps → Install. iOS build numbers are `10.<hours since epoch>.<minute*10 + attempt>` (attempt 0 for local builds), so CI and local uploads sort by time
- Sub-issue link: `gh api -X POST repos/<o>/<r>/issues/<epic>/sub_issues -F sub_issue_id=<issue .id>`
- PR check: `gh pr view <n> -R <o>/<r> --json closingIssuesReferences,commits`
- radar-ng native app build: `gh workflow run build-ios.yml -R mitchross/radar-ng --ref <branch> -f scheme=radarng`. Check the runner first, see the CI/native reference.

## Procedure
1. **Sync read-only.** Run `git fetch` and `git merge --ff-only origin/<default>` in the repo, then note the short SHA. Every card body cites it.
2. **Lightweight swarm via `delegate_task`** (no epic/Kanban wanted, e.g. a GitOps repo): clone the repo fresh into `$TMPDIR` at the pinned SHA and give every task the FULL brief inline in its `context`: repo path + SHA, the user's scope, the load assumed, read-only rules, what to look for, the four-part finding shape and "list what you did not read". Never pass a placeholder or a shared variable name, because children see only their own context: a briefless child guesses, reads the shared checkout on someone's feature branch, and invents claims. A `steer` lands only at the child's next tool boundary, so fast children finish without it; stop and re-dispatch instead of steering a wrong brief. Split areas so each child stays under ~8-10 findings, then merge into one numbered report yourself. Run phases in the order the user names (e.g. k8s → docs → rest), continuing the numbering across reports.
   **Model-pinned swarm via `claude -p`** (the user names Sonnet/Haiku subagents; `delegate_task` children inherit the parent model): write one full brief per area to scratch (same contents as above, plus a finding prefix and "at most 10 findings"), then run `scripts/run_claude_audit.sh <brief-dir> <prefix>:<model> ...` as one background `terminal` call with `notify=true`. Each auditor is read-only (`Read,Glob,Grep` only) and writes `audit-<prefix>.md`. Use Sonnet for parsing, auth and security areas; Haiku only for shallow areas (docs, config lists). Split ~3k lines per auditor (~3-5 min each). Auditors on neighbouring areas report the same bug twice (open redirects, URL encoding, fan-out caps), so merge them into one fix ID and keep a mapping table (fix ID → auditor IDs) at the top of the merged report.
   **Build the Kanban swarm** from the `hermes-agent` template. Use `workspace_kind="dir"`, `workspace_path=<repo>` and one worker per scope, each with a finding prefix (B backend, F frontend, C contracts, D debt). Each body carries the hard rules: read-only, file:line evidence, a numbered result. Give the synthesizer the report path `/opt/data/workspace/audits/<repo>-audit.md` and the Must/Should/Nice grouping, and tell it to keep the finding numbers. When the user names fewer prefixes than workers, give the extra worker a number range under an existing prefix (e.g. debt as C100+) so IDs never clash, and tell the user.
3. **Show the board** (`kanban ls`). The dispatcher ticks every 60 s. The board is shared by every swarm and runs a capped number of workers at once, so a card sitting in `ready` is waiting for a slot, not a duplicate swarm. Mention any other swarm on the board so the user expects the wait.
4. **Ping on completion.** Start a background `terminal` watcher with `notify=true`. It loops on `kanban ls` every 30 s, exits 0 when the synthesizer card is `done`, and exits 1 on `blocked`. Report the counts and the top fixes from the report.
   **Spot-check before reporting.** Child findings are self-reports and often wrong: re-prove every Must item and each surprising claim with one command (`count(<metric>)` in Prometheus for an alert rule, a grep of the latest default-branch CI log for a "silent gate" claim, a grep of `.github/workflows` before "tests never run", `kubectl get` for live drift). Drop or fix what fails, and say in the report which claims you dropped. Drop anything a code comment records as a deliberate decision.
   **Respect the user's scope.** For homelab/GitOps repos the user wants Argo, Kubernetes correctness and practices (sync, rebuild/DR, backups, drains, upgrades, drift, dead config), not security hardening: LAN-only credentials, unauthenticated internal UIs, RBAC breadth and network policy are out unless they cause a real bug. Put that exclusion in every child brief up front.
5. **Check first:** `gh issue list -R <o>/<r> --label ponytail-audit --state all` and `gh pr list --state all`. Another chat tab may have filed this same report and shipped part of it already; then continue under that epic instead of filing duplicates.
   **File issues** (`to-tickets` style; skip the quiz when the user already named the issues). Run `scripts/file_audit_issues.py --repo <o>/<r> --report <path> --sha <sha> --must --fix-first <extra ids> --hold <design ids>`. `--must` files every Must item. If the report has 0 Must, offer the top Should items and let the user pick. It:
   - creates the label;
   - creates one issue per fix-first id;
   - creates the epic with a checklist of every `### <ID>. <title>` heading, with issue numbers linked;
   - posts the full report as an epic comment;
   - links the issues as sub-issues of the epic.
   Check that the checklist count matches the report's finding count. For a later batch, pass `--epic <n>` to file new issues under the existing epic, and pass the report that contains each id (`--fix-first` ids missing from `--report` are skipped). When a batch mixes ids from the first and the follow-up report, run the script once per report. It links them as sub-issues and adds the issue numbers to the checklist lines. Given a follow-up report whose ids aren't in the epic yet, `--epic` also appends a "Follow-up audit" checklist section and posts that report as a comment.
6. **Make a worktree** for the fix: `git worktree add -b fix/<slug> /opt/data/workspace/<repo>-<slug> origin/<default>`.
7. **Get the gates runnable before the hand-off.** Read AGENTS.md's "Verify before you say done" table. Install missing tools on the PVC and export them in an env file. For radar-ng:
   - Rust: `RUSTUP_HOME=/opt/data/tools/rustup rustup toolchain install <rust-toolchain.toml channel> --profile minimal -c clippy,rustfmt`
   - Bun at the CI version: extract the `bun-v<ver>/bun-linux-x64.zip` release into `/opt/data/tools/bun/bin`
   - protoc: extract the protobuf release zip into `/opt/data/tools/protoc`, then set `PROTOC` and `PROTOC_INCLUDE`
   - Rust repos: build and `cargo test` the default branch once before the hand-off, save the pass count as the baseline, and export `CARGO_TARGET_DIR` to that prebuilt target. The fix agent then starts warm (a wreq/boringssl cold build is minutes) and the PR can compare its test count against the baseline.
   - YAML/Compose/workflow parse checks (no Docker, no PyYAML in the pod): `mkdir -p $TMPDIR/yamlcheck && cd $TMPDIR/yamlcheck && bun add yaml`, then parse with `bun -e "require('yaml').parse(...)"` from that dir. Give the agent that path; don't point it at a repo `node_modules`, because a fresh worktree has none and the gate silently doesn't run. If the agent still reports the gate as not run, run it yourself and post the result as a PR comment.
8. **Write the fix prompt** from `templates/fix-prompt.md`: issue numbers, scope, the gates, commit-and-push-early, the exact `Closes #N` lines and `Part of #<epic>`, never merge. Start each batch from a fresh copy of the template, not from the last batch's prompt. Copied prompts drop rules added to the template later (e.g. the partial-fix `Part of` exception), and the agent then ships `Closes` for a half-done finding.
   - If a batch fixes only part of an issue (e.g. one code path of two), the PR body says `Part of #N`, not `Closes`, so the issue stays open for the rest.
   - If another open PR edits the same file, name the lines it touches and tell the agent where to put its change instead. Otherwise the two PRs conflict at merge. Also name the directories it must not touch.
   - Say "line numbers are from an older commit; find the code by content", because earlier batches shift lines.
   - For a limit or cap fix (max names, max body, max fan-out), tell the agent to first check whether a normal flow sends large input down that path (e.g. a front page built from the user's whole subscription list) and to cap only the abuse-only path otherwise. A cap on a shared path breaks power users silently.
   - For a shared guard helper (redirect sanitizer, escaper), review each call site's input shape yourself: callers that strip or add a leading `/` before the helper can turn every real value into the fallback.
   - For a missing-dependency fix, tell the agent to add the manifest line without re-resolving (match the version already in the lockfile), prove it with `npm ci`, and keep the lockfile diff to that package. A plain `npm install` resolves a newer version and rewrites unrelated lockfile entries.
9. **Launch** `scripts/run_claude_fix.sh <worktree> <prompt> claude-sonnet-5-5 <env-file>` as a background `terminal` call with `notify=true`. First run `df -h /opt/data`: above ~85% the agent's cargo build fills the PVC mid-run. Free space by deleting `target/` (and `node_modules/`) in worktrees whose PR shows `MERGED` and that no process is using (`ps -eo args | grep -E 'cargo|claude'`). Other tabs' merged worktrees count too; leave unmerged ones alone and ask. Use Sonnet with `--effort high` for spelled-out fixes, and keep Opus for investigation. The script passes the env through `--settings` so Claude's Bash sees the toolchains. Set `EXTRA_TOOLS="Bash(curl *),Bash(python3 *),Bash(bash *)"` when the checks need tools beyond cargo, bun and git, for example CI or script fixes. For npm + Python repos use `EXTRA_TOOLS="Bash(npm *),Bash(npx *),Bash(node *),Bash(python *),Bash(ruff *),Bash(pytest *),Bash(mkdir *)"`, and copy the gate commands from `.github/workflows/*.yml` when the repo has no AGENTS.md. For new tests, tell the agent each one must fail without its fix. Before launching, tell the user not to merge Hermes config PRs until the PR link comes back.
10. **Verify, then report.** Check the PR's `closingIssuesReferences`, its commits and CI.
    - Re-derive the gate numbers from the agent's logs rather than trusting its summary. If a log was hand-written (the agent says a redirect was blocked), rerun that gate yourself before reporting it; add `Bash(tee *)` to `EXTRA_TOOLS` so the agent can log with `| tee`. For example, sum the `test result:` lines: `awk '{p+=$4; f+=$6} END {print p, f}'`.
    - Read any `FAILED` or `panicked` hit in context before calling it a failure, because test names contain those words.
    - Any gate the agent reports as "not run here" (a validate script, a YAML/Compose parse, a schema check), run it yourself from the worktree and post the real output as a PR comment before calling the PR ready. The same goes for a claim the agent couldn't verify (e.g. its docs lookup was denied, so a platform capability rests on the issue text): look up the primary docs yourself and post the links as a PR comment. Don't pass the gap on to the user. For behaviour that lives in upstream source (e.g. how a native map engine picks tile zoom), read the code at the exact release tag the repo pins: find the file with `gh api "search/code?q=<symbol>+repo:<o>/<r>" --jq '.items[].path'`, then `gh api "repos/<o>/<r>/contents/<path>?ref=<tag>" -H "Accept: application/vnd.github.raw" | grep -n <symbol> -A8`. Paths move between `main` and old tags, so try both, and quote the tag plus file:line in the comment.
    - When the agent shows the audit's suggested fix can't work (e.g. it sets a variable in a script that never runs the step that reads it), accept `Part of #N`, keep the issue open, and plan the real fix for a later batch rather than forcing the suggested one.
    - Read the agent's own design choices for side effects in the other direction before accepting them, especially anything that orders versions, build numbers or priorities. An agent's "Merge Danger" note that names a lasting downside (e.g. "later CI uploads will be rejected") means the design is wrong: fix it on the branch yourself (one extra commit), update the body, and say in the report that you changed it and why.
    - If the agent says it couldn't update the PR body, apply the body file yourself with `gh pr edit <n> --body-file <file>`, then re-check `closingIssuesReferences`.
    - If the agent reports a finding as only partly fixed ("kept X because Y reads it") but the body still says `Closes #N`, change that line to `Part of #N` with `gh pr edit`, comment the leftover on the issue, and re-check `closingIssuesReferences` after a few seconds (GitHub refreshes it lazily). Otherwise the merge closes an issue that still has work.
    - When the agent says an audit claim was wrong, or deletes a branch as unreachable, read the reader or the gate yourself (e.g. the parent's mount condition) before you repeat the claim to the user.
    - Read the diff of any CI or workflow change yourself. Redacted output shows tokens as `***`, so grep the file to confirm the variable really is there.
    - Code the pod can't build (Swift/native), and CI changes that remove a safety net such as `continue-on-error`, need a real run of the workflow on the PR branch. See `references/ci-and-native-verification.md`.
    - Check the PR body's own Merge Danger claims that hinge on the live system (e.g. a new runtime dependency such as the tz database) read-only against the running pod, e.g. `kubectl -n <ns> exec <pod> -- python -c ...`. A claim nobody checked can stop the service at deploy.
    - When a fix adds a condition on another component's output (a summary field, a status flag), read the producer and confirm what the field means before accepting it, e.g. that `scraped` is the listing count and success always sets `posted: true`. A wrong reading silently turns every run into a failure or a success.
    - When a fix makes hidden errors visible, read the retry and fail-on-error policy that consumes them and name the interaction in Merge Danger, because surfacing errors can turn into whole-job retries.
    - Report the PR, epic and issue links plus a gate table with the real counts. Never invent a number. Don't merge, even when CI is green: Mitch merges. Save a short note to Hindsight.
    - **Write for the user, not the tracker.** Lead each fix with what changes for someone using the product and why it matters ("old lightning no longer looks fresh"), not with finding IDs or code names. Put the IDs in a table or at the end. Close with the ship steps in order (merge → release → GitOps bump, or merge → native build).

### Progress summaries
When the user asks what was audited and fixed, answer in plain English, grouped by who benefits, not by batch or finding ID:
1. **What we audited:** each pass in one line (scope, finding count, how many were real bugs), and note that a verifier dropped anything unproven.
2. **What we fixed and why it helps,** grouped as *what users see* (app/web/watch), *server* (memory, waste, dead code) and *releases/builds* (pipeline fixes, which are often the biggest hidden win, e.g. a release that never really deployed).
3. **In progress,** then a one-line score: fixed / in progress / left.
Get the titles from `gh issue list -R <o>/<r> --label ponytail-audit --state all --json number,title,state` rather than from memory.

For "how much benefit did we get", give measured numbers, not the report's estimates: `gh pr list --state merged --search "ponytail in:title" --json additions,deletions,files` for PR count and +/- lines, with test-file additions split out (paths matching `test|__tests__|_test.rs|.test.`), plus the finding counts per severity from the report headings. Compare against the audit's summed `Lines saved` claim and say plainly when the real shrink is smaller (shared modules and new checks add lines back). Lead with the user-visible bugs fixed, then end with a one-line verdict.

If the user then says "simple" / "in English", rewrite it with no finding IDs, no tables and no file names: about six numbered groups (wrong numbers fixed, settings now save, hidden problems now visible, safer for the user's accounts or data, less code, more safety checks), each 2-3 one-line bullets in the form "it used to X, now Y". Keep it under ~200 words and end with the user's one remaining step. When the user asks for "everything" the audits fixed, cover every audited repo, not just this chat's: loop the same `gh issue list` over each candidate repo (for Gitea repos, use the issues API, since `gh` reports them as not found), give each repo its own short section, and say which ones were fixed in another chat tab. The same pass also finds fix PRs that merged since your last check, so ship any release they left waiting (step 9) in the same turn.

### Between batches
1. **After the user says they merged**, check every PR they might mean with `gh pr view <n> --json state,mergedAt` first, including the GitOps bump PR. Users often merge one of two and think both landed, and a merge click often silently fails. If the PR is still `OPEN`, lead with that, give its check status, and start no ship step. Guard every post-merge script on a non-empty `mergeCommit.oid`, because `gh run list --commit ""` lists every recent run and looks like real release runs. Then run `git fetch` and fast-forward. For GitOps repos, verify every merged change live straight away: Argo apps not Synced/Healthy, pods stuck in `Init`/`CrashLoopBackOff`, the new image tags, newly firing alerts. Diagnose any fallout from the fix itself (`kubectl logs <pod> -c <init>`) and open the fix PR in the same turn, before reporting the merge as done. Confirm the issues closed with `gh issue list --label ponytail-audit --state all`, then tick their epic lines with `scripts/tick_epic.sh`. If a CI check is red, compare its failing step with the same workflow on the default branch (`gh run list --branch <default>`, `gh run view <id> --json jobs`). Report it as pre-existing only when the same step fails there too. Remove the merged worktree (`git worktree remove`). Worktrees holding `node_modules` and `target` take minutes each, so remove them from a script in a background `terminal` call with `notify=true`. A foreground call times out and can leave a half-deleted folder that has no `.git`, so `git worktree remove` then refuses it. Confirm its PR merged, then `rm -rf` the folder and run `git worktree prune`.
   - **Skip no-op deploys:** release-on-merge cuts a new image for any change under the component's path, even a comment. When the merged diff for that component has no runtime effect (comments/docs only, or a types-only / move-to-shared refactor with identical behaviour; check `git diff <prev-merge>..<merge> -- rust/`), don't open its bump PR and tell the user in one line why (it would restart pods for nothing). The next real release carries it; list the skipped PR in that bump's notes so the user knows it ships too.
   - **Several merges at once:** each merge starts its own release run, queued in one concurrency group, and a no-op merge (CI-only, docs) would still burn a version tag. List the runs per merge commit (`gh run list --commit <sha>`); `gh run cancel` the no-op merge's release while its jobs are still before `publish` (check `--json jobs`), and point the bump script at the run for the newest merge, which carries every earlier one. Never cancel a run already in `publish`, because it can leave tags on some images and not others.
   - **Deploy step:** before opening a GitOps bump PR, check whether the repo's release workflow opens one itself (`gh pr list -R <gitops-repo> --state all --search "<repo> in:title"`). If it does, tell the user to merge that PR to deploy and don't open a duplicate. Say plainly that live still runs the old tag until then. Confirm a deploy from the pod, not from Argo: `kubectl -n <ns> get deploy -o jsonpath='{range .items[*]}{.metadata.name} {.spec.template.spec.containers[0].image}{"\n"}{end}'` plus the app's version endpoint via `kubectl exec`. An old Temporal worker version running next to the new one is normal while pinned runs drain. GitOps app-bump PRs don't restart Hermes, so they are safe to merge during a fix run. Release-on-merge cuts one tag per merge, and a later tag contains every earlier merge (check with `git rev-list -n1 <tag>`), so when two bump PRs are open, tell the user which fixes each one ships; merging the newest alone deploys them all.
2. **Pick the next batch by how it ships.** Group server-side fixes, which go out in one backend release, apart from app fixes, which need a native rebuild. Keep each batch to about 3 small, spelled-out findings. Re-read each candidate's file:line on the new default-branch head before filing, because earlier batches move lines. Don't hand an `unverified` finding to Sonnet as-is: first settle it yourself with a read-only live check (e.g. `kubectl -n temporal exec <admintools pod> -- temporal schedule list --namespace <ns>` for "is this schedule gone", or `curl -X OPTIONS <host> -H 'Origin: …' -H 'Access-Control-Request-Headers: …'` for a CORS claim). Post the command and result plus the decided fix as an issue comment, then batch it. If no live check can settle it (e.g. whether old app builds read a field), ship only the half that is safe either way (e.g. stop an unread field from gating the cache, but keep requesting and returning it), have the PR list which fields are read and unread, and leave the risky half on the issue. An `unverified` claim that the code itself can settle (e.g. "a frame only enters the manifest after all zooms are written") may go to Sonnet if the prompt makes it quote the proving code in the PR body and fall back to `Part of #N` with no change when it can't. For radar-ng web/app duplication findings, tell the agent the shared module goes in `web/src/shared/` with a one-line re-export in `frontend/src/lib/`, and that code called from a Reanimated `'worklet'` must not be swapped for a plain import (ship `Part of` instead), because a non-worklet function crashes or silently fails on the UI thread. Put first any finding that the previous PR's Merge Danger named as a side effect (e.g. surfaced errors now trigger whole-source retries), so the side effect is short-lived. Group by area (scraper, worker, dashboard) so batches don't touch the same files as an open PR. Up to two heavy fix runs (cargo or jest) may go in parallel only with disjoint file sets and halved workers (`cargo -j 2`, `--maxWorkers=2`), plus the other run's files named as off-limits in each prompt; at default worker counts parallel runs starve the pod. A Swift/native batch is a third lane when the Mac is free, since its compile runs on the Mac, not the pod. Once about 3 fix PRs (plus their bump PRs) await the user's merge, stop starting batches, list what to merge in order, and name the next batch for a "keep going"; more open PRs get lost and raise conflict risk.
   - **"Go till completion, don't ask" mode:** this overrides the ~3-open-PR stop. File every remaining finding in one `--epic <n> --fix-first <all ids>` run, settle every `unverified` item live first (above), then plan the rest as area batches (scraper+runner, worker, backend Python, frontend JS), each up to ~8-13 small findings, one commit each. Up to two fix runs may go in parallel when their files are disjoint and the gates are light (npm/pytest, not cargo or Jest); copy the launcher script for each parallel run. An area that shares a file with an open PR may still start if the prompt names the exact lines/functions that PR owns and forbids touching them; otherwise it waits for the merge. Fix any later conflict by merging the default branch into the fix branch, never by force-push. Keep going on each merge without asking; still never merge.
   - **Reading a per-number decision reply** ("1 ok, 9 don't believe you, 11 hold, 15 maybe"): "ok" → fix; "maybe"/"prolly" → decide from evidence and include it when low-risk; "hold"/"idk" → out-of-scope list; "don't believe you" → re-verify live yourself, show the evidence in the reply, and keep it out of the PR unless the change has zero runtime effect (e.g. deleting undeployed files). For an "X runs but nothing uses it" claim, also look for documented intent before re-asserting it: comments next to the setting and the user's sibling or starter repos (`gh search code "<symbol>" --owner <user>`). A component kept on purpose is a decision, so drop the finding and say why; "don't care" → the cheapest form of the fix (e.g. a label, not a backup). Must-fix items the user skipped in the reply still go in; say so in one line. Any item where the user's answer reveals the audit claim was wrong: say so plainly.
   - **"Do them all in one big PR" mode:** when the user asks for every remaining finding in one PR, that's allowed (it's one PR against the default branch, not a stack). With no epic (the user only wants the PR), skip issue filing and make commit subjects carry the finding numbers. File any finding that has no issue yet, write one prompt that orders the findings by risk (deletes first, worklet/native/build items last), one commit per finding, `Part of #N` for anything unfinished, and an explicit out-of-scope list for items waiting on the user's design. Give the agent a fallback for each risky item (e.g. "if the bundle doesn't prove the shared function is a worklet, revert that commit"). Run the Mac branch build before calling it ready.
   - **Before saying "all in PRs":** prove the open fix PRs combine. Make a detached scratch worktree from the default branch, `git merge --no-edit origin/<branch>` each open fix branch in turn (report any conflict and abort), run the full gates on the result (`scripts/run_npm_py_gates.sh <wt> <logdir>` for npm + Python repos), then remove the scratch worktree. Report the combined counts and say the PRs merge in any order.
3. **Before proposing a new repo audit**, check `gh issue list -R <o>/<r> --label ponytail-audit` on each candidate repo. Another chat tab may have already audited it.
4. **When the user hands you the decisions** ("you make the call", "do all"; also items an earlier PR left as "waits on a decision"), decide each open item from code and docs evidence. Post the decision and the reason as a comment on that item's issue, or annotate its epic line (e.g. kept, not dead code). Then start the next batch without asking. Merging stays with the user, though: say so in one line and keep going.
   - If the user asks you to merge or auto-merge the fix PRs, still decline: merging is a hard rule only the user can change. In one line, offer GitHub's native auto-merge instead (they turn on Settings → General → Allow auto-merge, then click "Enable auto-merge" on each PR, and GitHub merges it when CI is green), or a PR that changes the rule for them to merge. Then keep working.
   - If the user asks for stacked PRs to go faster, decline: on merge GitHub deletes the base branch and closes the child PR instead of retargeting it, and every PR still needs its own CI, Mac build and merge click. Offer disjoint parallel batches, each against the default branch, and name the real bottlenecks (a sleeping Mac, merge clicks that didn't land, cold CI builds).
   - **Presenting a design-blocked finding** (one parked on the user's choice): research before you offer options, because otherwise the user asks to "google it first", then "alternatives?", then names sibling libraries one by one. Search wide on the first pass:
     - the current library: its docs and API stability labels ("Experimental, do not use");
     - its issue tracker (`gh api repos/<o>/<r>/issues/<n>` plus `/comments` reads issues when page extraction fails);
     - built-in features that may already solve it: scan the style spec or layer list for anything new. Confirm support in the exact wrapper version the repo pins by grepping its npm tarball (`npm pack <pkg>@<ver>`), because the repo's `node_modules` may not exist;
     - competing libraries the user would think of (for a React Native map: expo-maps, react-native-maps, rnmapbox).
   - **Lead with a plain explanation** of the bug, using an everyday analogy (e.g. "a clear sheet laid on top of the whole map"), before any table. Then give:
     - a per-platform table (web / iOS / Android: how it renders, whether it's affected);
     - who is hit by default (feature flags that are on by default);
     - an options table with effort and risk, each claim linked to its source.
     If the user says "I don't get it" or "talk to me in English", drop the tables and IDs entirely and retell it as the analogy plus the fix in about 150 words.
   - **Before recommending a replacement, read why the current design exists** (the repo's design doc for that feature, e.g. a "why" section with measured bottlenecks) and check the candidate keeps that win. Pin down which upstream knob the trick depends on (e.g. a custom data encoding) and confirm it ships in the pinned native library and wrapper. A rendering fix that brings back the network cost the current design removed fails the bar, and walking back a recommendation the user already said yes to costs a turn.
   - **Filter the options through the product's stated goals before recommending.** For radar-ng those goals are:
     - a premium app that is never slow or janky;
     - every weather data overlay (radar, warnings, storms, forecast) comes from the user's own server, because we are the API and use few third-party APIs;
     - the base map underneath may be native (Apple/Google) or React Native;
     - CarPlay is a wildcard: use whatever Apple requires (MapKit basemap, Apple search and routing).
     Drop any option that costs smoothness, moves data off the user's server, or adds a paid or third-party SDK, and say so in one line.
   - **"Google it harder" / "think harder" means search wider, not build heavier.** Don't escalate to a bigger engineering option. Look for simpler paths using standard features you haven't checked yet, e.g. other ways to hand data to the engine: local `file://` tiles, PMTiles, custom protocol handlers, image sources. Check each upstream PR's real state (`gh api repos/<o>/<r>/pulls/<n> --jq .merged_at`), because a merged-sounding title can be unmerged.
   - **When the recommendation needs a feel test on a device,** never propose a hidden toggle: the user asks why it isn't simply the default. Use a visible Settings switch between the old and new engine. If the user will test it soon, make the new one the default and keep the old one as a fallback for a build or two. If they say "do what's best, I'll test later", keep the old default, ship the new engine behind the switch, and file a follow-up issue with a device checklist (layer order, smoothness, pan lag, time to first frame, memory, storage, Android) and the decision rule (pass → make it the default and remove the old path; fail → the named fallback option). Mark the PR `Part of #N`, and comment the plan and the ruled-out options on the design issue.
   - **A feature the pod can't run (a new render path, native I/O) must be debuggable from the phone.** Put this in the fix prompt from the start:
     - record every failure stage and message instead of swallowing it in `catch {}`;
     - show a one-line status in Settings, and send the same counts to the app's existing telemetry;
     - fall back automatically to the old path when nothing works within a few seconds, so the user never sees a blank screen.
     Otherwise "it shows nothing" gives no clue which step failed. When the user says they'll test on a Mac simulator, file a hand-off issue from the "Simulator test hand-off" recipe in `references/ci-and-native-verification.md`.
   - **Before calling such a PR ready, read its diff yourself** for silent catches and for math that has to match the engine it feeds. Example: MapLibre Native picks raster tile zoom by *rounding* (`coveringZoomLevel`), so tiles written at `floor(zoom)` are never requested at x.5-x.99. A green Mac build only proves it compiles.
   - **Answer "when will upstream fix it" with evidence:** whether any issue exists, its state, and whether we need it at all. Then end with your pick and a single yes/no.
   - When the user says "u tell me" to a won't-fix question, decide it, tick its epic line with a `(won't fix): <reason>` annotation (findings with no issue only need the epic edit), and report the reason in one line.
   - Once the user has said "keep going" / "don't ask, just go", never end a status reply with "say go" or a menu of next batches. Pick the next batch by the rules in step 2, file it, launch it, and report what is now running. A closing question in that mode reads as stalling.
5. **A fix run can die silently** (e.g. when the chat switches interface): the `.json`/`.err` outputs stay 0 bytes and no completion notice arrives. When a run's check logs stop updating for ~15 min, check `ps -eo pid,etime,args | grep "claude -p"` (a bare `pgrep -af` count matches its own shell, so read the args) and look for gate processes. If none, check `git ls-remote` for pushed commits, then finish it yourself: review the diff, run the gates (`scripts/run_npm_py_gates.sh` for npm + Python repos), write the PR body with the real counts, and open the PR. That's cheaper than relaunching Claude; tell the user the PR is yours.
6. **After an interrupted turn**, check the `claude -p` processes and the branch state before saying a run is going. An interruption can land between writing the prompt and launching it.
7. **Close coverage gaps with a follow-up swarm.** After the first pass, list the areas no worker read: typically `deploy/`, CI workflows, native targets (Swift/Kotlin, config plugins) and docs. Tell the user, and on a yes run a small follow-up swarm, e.g. an ops worker (O) and a native worker (N).
   - Each worker reads the first report's headings and skips anything already in it.
   - The synthesizer writes `<repo>-audit-2.md` in the exact same `## Must` / `### ID. title` format, so `file_audit_issues.py --epic <n> --must` can append it to the same epic.
   - The swarm is read-only, so it can run alongside one fix run.
8. **Re-check the user's pending steps against new findings.** When a finding breaks something the user is about to do (e.g. the release pipeline re-uses a version tag), tell them to hold that step, and fix the finding first.
9. **Ship the merged fixes.** Shipping isn't done at merge.
   - Server fixes: release, then a GitOps digest bump PR, then a live pod check.
   - App fixes: one native build from the default branch, then the user's on-device checklist. Once the user has set up TestFlight and asked for builds that way, the default ship step after each merged app batch is a `testflight=true` build from the default branch; in keep-going mode dispatch it without asking.
   - The user often merges while a gate or `claude -p` run is still going. Before any status reply ("now what", "send it"), run `gh pr list -R <o>/<r> --head <branch> --state all --json number,state` for each in-flight batch, not just `pgrep`. A live `claude -p` process doesn't mean the PR is still open. If it's merged, skip "ready to merge" and go straight to the ship step (release run → GitOps bump PR).
   - The recipes are in `references/ci-and-native-verification.md`.
   - When a TestFlight build is still queued or being rerun on an older commit and another app batch merges, `gh run cancel` it and dispatch a fresh `testflight=true` build from the default branch; one upload with everything beats two. Stop its watcher by letting it exit on the cancel, not with `pkill -f <pattern>`: the pattern also matches the shell running pkill and kills your own command.
   - When the user says a runner or machine "should be online now" or "is online", check the runners API and the run's job status again before replying, then report the steps that already passed. The runners API can show `offline` for a minute after the Mac wakes, so never repeat "offline" from an earlier read; dispatch the build anyway, because a queued job starts by itself once the runner connects.

10. **Close the audit** once every finding's PR has merged. When the user says "close out issues", close the ones whose fix is verified live. For a feature nobody has run on a device yet, keep its test issue open and say why in one line: it is the only tracker, and the device test often finds it broken, which forces a reopen. Re-check that `gh issue list --label ponytail-audit --state open` shows only the epic. A finding parked on the user's design decision doesn't block closing: when the user says to close it out, tick its epic line with "moved out of this epic, tracked on #N", comment the same on that issue, and leave it open on its own. Tick every remaining epic line, then close the epic with a one-line comment that lists the fix PRs, the live versions and the TestFlight delivery, and names any follow-up outside the repo (e.g. a desktop runner rebuild). Before closing, smoke-test the final release's new behaviour from the pod (e.g. `curl` the in-cluster service for a new manifest field, and expect 404 on a deleted route), not just pod readiness. Find the endpoint paths with `grep -rhoE '\.route\("[^"]+"' <api src>` instead of guessing. Remove every fix worktree, plus any other tab's worktree whose PR shows `MERGED`, and prune. Wait for the final release's GitOps bump PR (a background watcher that polls `gh pr list --search "<repo>: v<next> in:title"`, then `gh pr checks --watch`), and hand that PR to the user. After they merge it, confirm the live version from the pod.

11. **Hand off desktop-only follow-ups as a paste-ready prompt.** Some fixes only take effect on the user's machine (e.g. a locally built runner image such as deal-scout's `deal-scout-runner:local`). Read the component's README and compose file first, then give a Claude Code prompt that:
    - finds the local clone, and stops and shows any local changes before `git pull --ff-only`;
    - records the old image ID, rebuilds and restarts only that service;
    - proves the fix with an observable check (e.g. `time docker compose stop <svc>` well under 10 s and exit code 0, not 137), then shows one cycle of logs;
    - forbids deleting volumes (`down -v`) and re-running login steps unless the logs demand it, and never commits or pushes.
    Add one line on what "good" looks like. If the user pastes such a desktop prompt into the Hermes chat instead, don't attempt it: say in one line that it needs Docker on their own machine, which the pod can't reach, and tell them to paste it into Claude Code there. If the desktop agent reports untracked files blocking the pull, recommend backing them up to a dated folder in the home directory (not a scratchpad that gets cleaned), then pulling; building from a side worktree leaves the clone behind and the same block returns next rebuild.

### After a Hermes restart
1. Check the live state, not memory: `kanban ls --status running`, `git -C <worktree> status -sb`, `git log origin/<default>..HEAD`, `git ls-remote origin <branch>`, and `gh pr list --head <branch>`.
2. **Reclaim orphaned cards.** A card left `running` has a dead worker. Run `kanban reclaim <id> --reason "pod restart"` for each one. That ends the worker, releases the claim, restores the card's earlier status and resets its failure counter, so the dispatcher re-runs it on the next 60 s tick. Then confirm with `kanban ls` and `kanban diag`.
3. **Resume the fix run** from whatever survived: pushed commits, or uncommitted edits in the worktree. The prompt template tells Claude to keep existing work and never redo fixes. Relaunch step 9.

## Pitfalls
- **CLI swarm bodies:** `hermes kanban swarm --worker profile:title:skill` uses the title as the whole body. Use the Python template for real instructions.
- **Verifier skill:** the default verifier skill `requesting-code-review` auto-fixes code. Swap it to `ponytail-review` for read-only audits.
- **Desktop pings:** Kanban `notify-subscribe` needs a messaging platform and chat id, so it can't reach a desktop chat. Use the background watcher.
- **Don't merge Hermes config PRs while jobs run.** Each merge rolls the pod: a new ReplicaSet and image pre-pull, not a crash or OOM kill. The rollout kills every running agent, swarm worker and background watcher. Queue those merges until the PR link is back. Make the fix agent commit and push before the slow gates, so a rollout costs only check time.
- **Orphaned Kanban cards.** After a restart, cards can stay `running` with no worker. The dispatcher's orphan and stale sweeps (`kanban.reconcile_orphans`, `kanban.dispatch_stale_timeout_seconds` = 14400) may take hours. Reclaim them by hand (see After a Hermes restart).
- **Blocked Claude Bash:** in `claude -p`, Bash calls to unlisted tools come back "requires approval". Allow `Bash(bun *)`, `Bash(cargo *)` and so on, and pass PATH and other env through `--settings '{"env":{...}}'`.
- **Rust toolchain:** `/opt/rust/rustup` is read-only, so set `RUSTUP_HOME` on the PVC. Run cargo from inside `rust/`, because outside it `rust-toolchain.toml` is ignored and a newer clippy flags unrelated files.
- **libclang for bindgen (wreq/boring-sys2, e.g. redlib):** the pod has no libclang. `python3 -m venv /opt/data/tools/venvs/libclang && .../bin/pip install libclang`, then export `LIBCLANG_PATH=<venv>/lib/python3.*/site-packages/clang/native` and `BINDGEN_EXTRA_CLANG_ARGS="-I$(gcc -print-file-name=include)"`. redlib's env file is `/opt/data/tools/redlib-env.sh`. No cargo-nextest in the pod; `cargo test` is the local gate.
- **Issues disabled on the repo** (e.g. mitchross/redlib, a fork): skip filing, use the "one big PR" mode with F-ids in commit subjects and a mapping table in the report. Don't flip repo settings to enable issues without asking.
- **Answering "what models are the subagents?"** Give a short table: role, model, state (auditors / verifier / fix agent), and one line on why a cheaper model wasn't used where it wasn't.
- **protoc:** the Temporal SDK build needs protoc *with* the well-known `.proto` includes. A bare `/usr/bin/protoc` fails on `field_mask.proto`.
- **Cap test workers at 4.** Jest's default spawned 11 workers, starved the pod, and the run died. Always pass `bun run test -- --maxWorkers=4`, and run gates one at a time, not in parallel.
- **Long `cargo test`:** a radar-ng `cargo test --workspace` takes more than 10 minutes, and Claude Code's background Bash kills a command at that limit. Tell the agent to run it in the background with output going to a log, give it a 2-hour limit, and poll.
- **Environment-only failures:** tests that shell out to tools missing from the pod (e.g. `ruby` in `podDeploymentFloor.test.js`) fail locally only. Report them as an environment gap, not a code failure.
- **Report format drifts:** synthesizers may write findings as `**ID. title**` instead of `### ID. title`, which `file_audit_issues.py` doesn't parse. Dry-run the parser and assert the count before filing. Convert a copy with `sed -E 's/^\*\*([A-Z][0-9]+)\. (.+)\*\*( \(.*\)| \*\(unverified\)\*)?$/### \1. \2\3/'` and pass that copy to the script.
- **Gitea repos:** use the API with `$GITEA_TOKEN` (`/api/v1/repos/<o>/<r>/issues`, `/labels`, `/pulls`). Gitea has no sub-issues, so mark the epic blocked by each issue (`POST /issues/<epic>/dependencies` with `{owner,repo,index}`) and add `Part of #<epic>` to each body. Claude can't open Gitea PRs from the pod, so have it write the title and body to scratch, then open the PR from the parent.
- **Don't edit a launcher script while a background run uses it.** Bash reads scripts as it goes, so copy it to a new file for the second run.
- **Stale watcher notices:** a watcher on a run you cancelled or superseded still fires (exit 1 for a cancelled run, 143 if killed). Answer it in one or two lines: say it's the old run and name the live watcher and what it waits on, so the user doesn't read it as a new failure.
- **Transient GitHub GraphQL errors** ("Something went wrong while executing your query") on `gh pr create` or `gh issue create` often happen after the object was created. Run `gh pr view <branch>` / `gh issue list --search "<ID>: in:title"` first, then retry only what's missing; rerunning `file_audit_issues.py` with the already-filed ids makes duplicates.
- **Accidental auto-close:** GitHub treats "close/closes/fix/fixes/resolve #N" anywhere in a PR body as a closing keyword, even in "does not close #N". The fix-prompt template forbids those words before issue numbers outside the exact `Closes` lines; when a body still has one, reword it ("#N stays open") and re-check `closingIssuesReferences`.
- **Counts:** verifier metadata counts can be stale. Count the findings from the report headings.
- **Extra files:** workers may write their own findings files next to the report. That's fine; the repo itself stays clean.

## Verification
`gh pr view <n> -R <o>/<r> --json state,closingIssuesReferences --jq '{state,closes:[.closingIssuesReferences[].number]}'` shows `OPEN` (never `MERGED` by us) and exactly the fixed issue numbers, without the held ones.
