# CI and native verification for fix PRs

Load this when a fix batch touches code the Hermes pod can't build or run (Swift/Kotlin/Xcode targets, iOS/Android packaging), or when it changes CI workflows. That includes removing `continue-on-error` or touching release/tagging jobs.

## Rule
A claim that the code compiles or the workflow works needs a real run of the real workflow on the PR branch. Reading the YAML or doing `bash -n` doesn't count. A green PR CI isn't enough either when the job in question only runs on `workflow_dispatch` or on the default branch.

## Recipe: run a dispatch-only workflow on the PR branch
1. Check the self-hosted runner first:
   `gh api repos/<o>/<r>/actions/runners --jq '.runners[]|"\(.name) \(.status) busy=\(.busy)"'`
2. Dispatch on the branch, then grab the run id:
   `gh workflow run <file>.yml -R <o>/<r> --ref <branch> [-f key=val]`
   `gh run list -R <o>/<r> --workflow <file>.yml --branch <branch> --limit 1 --json databaseId,url`
3. Watch it in a background `terminal` call with `notify=true`:
   `gh run watch <id> -R <o>/<r> --interval 60 --exit-status > <scratch log>; gh run view <id> --json conclusion,jobs`
4. Confirm the specific step ran and passed, not just the run conclusion:
   `gh run view <id> --json jobs --jq '.jobs[].steps[]|select(.name|test("<step>";"i"))|"\(.name): \(.conclusion)"'`
   Then list the artifacts with `gh api repos/<o>/<r>/actions/runs/<id>/artifacts`.

- **Offline runner:** the run just queues. Tell the user to wake the machine (e.g. the Mac) and keep the watcher running, because it starts by itself once the runner connects. If the machine is awake but the runner still shows offline, have the user restart its LaunchAgent: `launchctl kickstart -k gui/$(id -u)/actions.runner.<owner>-<repo>.<runner name>`.
- **Run fails with blank step conclusions and no step log:** read the job's check-run annotations (`gh api repos/<o>/<r>/check-runs/<job databaseId>/annotations`). "The self-hosted runner lost communication with the server" means the machine slept or dropped mid-run, not a code failure. Queue `gh run rerun <id>` right away (it waits for the runner) and restart the watcher. If it keeps happening on a Mac on AC power, suggest `sudo pmset -c sleep 0` (display can still sleep). A job can also fail at "Set up job" with the same annotation when the runner picks it up and drops at once; that run executed no code, so say so and rerun. After repeated drops, tell the user it's fine to stop for the night: the queued run starts by itself when the Mac returns.
- **Dependency bumps are native changes.** A fix that runs `expo install --fix` (or any lockfile re-resolve) can move React Native from a release candidate to stable or cross a major (e.g. Jest 29 → 30). Read the `package.json` diff yourself, have the PR list every bumped package, and run the native build on the branch before calling it merge-safe, even when JS gates and bundle exports pass.
- **Splitting a workflow job** (e.g. a read-only PR job plus a write-scoped push job) renames a check. Check whether anything requires the old name before warning the user: `gh api repos/<o>/<r>/branches/<default>/protection` (404 = not protected) and `gh api repos/<o>/<r>/rules/branches/<default>`.
- **Build-only workflows** (sign and attach an artifact, no store upload) are safe to dispatch without asking. Workflows that upload, release or deploy need the user's yes.
- **Fix agents never dispatch workflows.** The parent dispatches after the agent pushes, so the run tests the pushed commits.

## When the pod can't compile the language
- In the fix prompt, tell the agent there is no compiler. It should read every referenced type and function before editing, and keep edits obviously type-correct.
- If the repo has check programs (e.g. `swiftc`-built presentation checks) that only run from a manual simulator script, add a CI step that compiles and runs them in the batch, so the dispatch run is a real test gate. Put that step in a spot no other open PR edits.
- The PR body says plainly that the code isn't compiled locally and that the dispatch run is the compile gate. Report that run's result before telling the user it's safe to merge.

## radar-ng specifics
- The iOS workflow is `build-ios.yml`, run with `-f scheme=radarng`, on the `[self-hosted, ios]` Mac runner `mac-ios`. It always produces an `ipa` artifact. It uploads only with `testflight=true`.
- App fixes reach phones only after this build. Batch app fixes so one build covers them, and ask the user to check visual changes (layer order etc.) on a device.
- A branch built before another merged PR (e.g. one that removed `continue-on-error`) can log `preflight FAIL` while the step stays green. Judge the step by the code on that branch, not by `master`.
- **Final device build:** after the last app batch merges, dispatch one build from the default branch (`--ref master`), not from a PR branch, so the IPA holds every merged fix. Report the run link, the steps that passed (Swift checks, preflight, archive) and the IPA size. Then give the user a short on-device checklist, one line per visual fix.
- **TestFlight:** the workflow has an opt-in `-f testflight=true` input. Uploading counts as a store action, so the first upload needs the user's yes; after the user has set up TestFlight and asked for it, a `testflight=true` build from the default branch is the normal ship step for merged app batches. It needs an App Store Connect app record, an API key on the Mac with at least App Manager, and an internal tester group. These are user-only steps in App Store Connect; list them, don't guess them. `ITSAppUsesNonExemptEncryption` is a legal declaration, so flag it for the user to confirm.
  - Don't upload via `destination=upload` in ExportOptions. It re-signs every framework inside Xcode's distribution pipeline, and on the headless Mac runner that re-sign can't reach the key (`errSecInternalComponent` on a framework), even though a plain `app-store-connect` export signs fine.
  - Keep the known-good export and add a separate upload step for the signed IPA: `xcrun altool --upload-app --type ios --file <ipa> --apiKey $ASC_KEY_ID --apiIssuer $ASC_ISSUER_ID`, with the IDs from `~/.ios-signing/env`. altool only finds the key at `~/.appstoreconnect/private_keys/AuthKey_<id>.p8`. Since Xcode 26 altool can exit 0 on a failed upload, so pass the step only when its log contains `UPLOAD SUCCEEDED`. Don't fail on any `ERROR` line: a good upload can still log a harmless `ERROR: ... CDUploaderStateInfoResumeFilePath` line, which marks a delivered build as failed.
  - **CarPlay is a prebuild switch:** CarPlay scenes, sources and the `carplay-maps` entitlement are added only when `RADAR_CARPLAY=1` is set at `expo prebuild`; preflight prints `CarPlay build: yes/no`. A CI/TestFlight build without it ships phone + Watch only and replaces the user's CarPlay-capable install, so check that line whenever the user reports CarPlay missing, and prove any change with a branch Mac build (archive and app-store export must sign with the entitlement) before uploading.
  - Prove a changed upload step by dispatching the workflow from the fix branch with `testflight=true` before you open the PR. Until one upload run succeeds, call the path unproven.
  - Mitch often merges an app PR before its branch Mac build finishes. Then chain it in one background script: watch the branch run, and dispatch the `testflight=true` build from `master` only if the branch run passed. If it failed on a code error, report the error and fix it in a follow-up PR, since `master` may now be broken. If it failed only because the runner lost communication (check the annotations), skip the branch rerun and dispatch the `master` TestFlight build directly: it compiles the same code and uploads in one Mac run, which matters when the Mac keeps dropping.
  - A branch run that passed `Swift checks` but dropped during `Archive and export` has not proven the build: `Swift checks` only covers the check programs, while the archive compiles every target. Tell the user the code is still uncompiled until an archive passes.
  - While a merged Swift change is still uncompiled on `master`, don't launch another native (Swift) batch; start only JS/server batches until a `master` Mac build passes, so a compile error has one suspect.
- **Build numbers:** `app.config.js` sets `ios.buildNumber` (plus CI's `IOS_BUILD_RUN`) only at `expo prebuild`, and `preflight-ios-release.sh` recomputes the same value. A fix that sets the variable in a script that skips prebuild (`build-ios-standalone.sh`) changes nothing; any real fix must reach prebuild or the xcodebuild settings and keep preflight in agreement, proven by one Mac build. CI and local builds use one clock-based value, `IOS_BUILD_RUN=<hours since epoch>.<minute*10 + n>` (n = run attempt in CI, 0 locally). Reject any scheme that just puts one side far above the other (e.g. local `9000.x`): after one such upload App Store Connect rejects every build from the other side. Keep each component under Launch Services' 21-bit limit (~2.1M), so use hours, not minutes, since epoch.
- **Shared Swift across targets:** `@bacons/apple-targets` links every file in `frontend/targets/_shared/` into the main app and every target (README `_shared` section; `globSync("_shared/*")` in its config plugin). Dedupe target copies into `_shared/`, and don't also add the file from a config plugin (e.g. the CarPlay plugin that feeds the main app), because the main app then compiles the type twice. Update any `swiftc` check lines in `build-ios.yml` to the new path.
- **Intermittent signing failure:** an `errSecInternalComponent` on export from a workflow whose last run on the same Mac was green is a host state problem (the signing keychain locked while the Mac locked or slept), not a code or workflow bug. Don't edit the workflow; tell the user to unlock the Mac and turn off the keychain's "Lock after…" / "Lock when sleeping", then rerun (or dispatch a fresh build if newer app code merged).
- **Reading a failed Xcode step:** the step log is huge. Save it, then grep for the real error: `gh run view <id> --log | grep -P "\t<step name>\t" | sed 's/.*Z //' > log; grep -n -A3 "codesign command failed\|EXPORT FAILED\|error:" log`. Use the raw timestamps (skip the `sed`) to time archive vs export.
- **Simulator test hand-off:** CI can't run the simulator, because the Mac runner logs `CoreSimulator is out of date … Simulator device support disabled`. When the user will test on their Mac, file one issue they can follow top to bottom:
  0. **Prerequisite:** update macOS or Xcode until that warning is gone. Pick a device with `xcrun simctl list devices available | grep iPhone`.
  1. **Build:** check out the branch, then in `frontend/` run `bun install --frozen-lockfile`, `RADAR_CARPLAY=1 bunx expo prebuild --platform ios --clean --no-install`, `pod install` with the `RUBYOPT` shim from `build-ios.yml`, and `bunx expo run:ios --device <UDID>`. The scripted alternative is `SIMULATOR_UDID=<UDID> bash scripts/test-ios-simulator.sh`.
  2. **Reproduce:** give exact settings and the zoom levels to try (include x.3 and x.7, because raster tile zoom rounds).
  3. **Evidence:**
     - the in-app diagnostics line;
     - logs from `xcrun simctl spawn <UDID> log stream --predicate 'process == "radarng"' --level debug`, filtered with `grep -iE` on the feature's keywords;
     - files the feature wrote, under `$(xcrun simctl get_app_container <UDID> <bundle id> data)/Library/Caches/<dir>`;
     - the telemetry events.
  4. **Pass checklist,** and ask them to paste the evidence back on the issue.

## CI build speed (Rust)
When the user asks for a Rust cache or faster builds, measure before you change anything:
1. Job times: `gh run view <id> --json jobs --jq '[.jobs[]|"\(.name) \(((.completedAt|fromdate)-(.startedAt|fromdate))/60|floor)m"]'` for the last few default-branch runs.
2. Cache hits: `gh run view <id> --log | grep -E "Cache hit for|No cache found|full match"`, and count `Compiling ` lines per job (`awk -F'\t' '/Compiling /{print $1}' | sort | uniq -c`). A job with a full hit recompiles only workspace crates; hundreds of `Compiling` lines mark the job that isn't cached.
3. Docker builds that compile Rust inside `RUN --mount=type=cache` get no benefit on GitHub runners: `cache-to: type=gha` stores layers, not cache mounts, so any source change recompiles every crate. Fix it by building the binary once on the runner (in the runtime's glibc container, e.g. `debian:bookworm-slim`) with `Swatinem/rust-cache`, uploading it as an artifact, and building the images with the Dockerfile's prebuilt path (`RADAR_FROM=prebuilt --build-context radar-bin=dist` in radar-ng). Keep the in-Docker source build as a step that runs only when the Dockerfile, its dockerignore or `rust-toolchain.toml` changed, or on `workflow_dispatch`, so the Compose path stays tested.
4. Give jobs that do the same build (same container, toolchain, profile) one `shared-key` so the CI run and the release warm each other. The first run after adding a new key reports `No cache found`; the speedup shows from the next default-branch run, so say so when reporting the PR's own timings.
5. Set expectations from what the cache stores: `rust-cache` keeps third-party crates only, so a full-match release build still recompiles the workspace crates (about 3-5 min for radar-ng). The real saving is the image job skipping the in-Docker compile (about 10 min down to about 1 min). Don't promise a 1-2 min binary job; report the measured times after the next merge.

## Backend and web rollout after fix PRs merge (radar-ng)
1. Merging `rust/` changes triggers `ghcr-backend.yml` on `master`. Runs queue in the `ghcr-backend-release` concurrency group, so two merges give two sequential releases (e.g. v2.0.17, then v2.0.18). Check that `ci · rust` is green on the commit you'll deploy.
2. Read each image's `tag@digest` from the run's `published` annotations. Don't predict them: `gh api repos/mitchross/radar-ng/check-runs/<publish job id>/annotations --jq '.[]|select(.title=="published")|.message'`. Get the job ids from `gh api repos/mitchross/radar-ng/actions/runs/<run>/jobs`.
3. In talos, follow `homelab-gitops-change-prs` (fresh clone if the shared checkout is broken; its image-bump pitfall covers digests and kustomize checks). Run `scripts/bump_radar_backend.sh <ghcr-backend run id> <ci-rust run id> <merge sha> <PR>` as a background `terminal` call with `notify=true` right after the merge; it waits for both runs, then makes its own worktree from `origin/main`, commits, pushes and prints the talos PR URL. Always use the script; don't build a new bump by sed-editing the last one, because version and digest patterns rewrite each other and the copy silently targets the wrong tag. The script reads the published digests, checks each against the registry, rewrites every ref and fails unless the render has all refs on the new tag. It bumps every ref together: the 5 worker pools in `my-apps/personal-projects/radar-ng/temporal-workers/worker-pools.yaml`, both open-meteo containers, and tile-server. Bump the web image only if `web/` changed since its pinned tag.
4. Run `kubectl kustomize my-apps/personal-projects/radar-ng`. Every ref must be on the new tag, with none left on old ones. Then open the PR and wait for `gh pr checks`. Mitch merges, and the worker pools smoke-test before promotion.
5. **Web image:** any merged `web/` change (or `ghcr-web.yml` edit) publishes a new `radar-ng-web` tag on its own, but nothing deploys it. After each such merge with a runtime effect, run `scripts/bump_radar_web.sh <ghcr-web run id> <merge sha> <PR> <notes.md>` in the background (notes = one markdown bullet per user-visible change, plus any earlier skipped web PR it now carries). It reads the tag@digest from the `published` annotation, checks it against the registry, and opens the talos bump PR for `deployment-web.yaml`. Skipping this leaves published tags undeployed (the pinned tag can trail several releases).
6. After the merge, check live, not Git. Argo can keep reporting `Synced Healthy` on the *previous* commit for several minutes until its next repo poll, so compare `kubectl -n argocd get application my-apps-radar-ng -o jsonpath='{.status.sync.revision}'` with the bump PR's `mergeCommit.oid`. Until they match, Argo simply hasn't polled yet; don't report the old pods as the result. Run a background watcher (`notify=true`) that loops every 30 s until the revisions match, waits ~2.5 min for the rollout, then prints sync/health, the pods and a count of image tags (`kubectl get pods -o jsonpath='{range .items[*]}{range .spec.containers[*]}{.image}{"\n"}{end}{end}' | grep -oE '<image>:v[0-9.]+' | sort | uniq -c`), and tell the user nothing is needed from them meanwhile. Once the revision matches, wait for `operationState.phase=Succeeded` before calling the deploy stuck. Then check `kubectl -n radar-ng get pods` (Ready, restarts, image tags) and the Argo CD app's sync revision. Report anything that changed outside your PR (e.g. a Renovate bump) as observed, not explained.
